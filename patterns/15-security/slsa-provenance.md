# SLSA Provenance

## 1. Name, aliases, and lineage

The canonical name is SLSA Provenance, the specific attestation
artifact produced under the Supply-chain Levels for Software Artifacts
framework, pronounced salsa. Google proposed the framework in
collaboration with the Open Source Security Foundation and published
it in a blog post, "Securing the software development lifecycle with
Cloud Build and SLSA", 30 July 2021
(https://cloud.google.com/blog/products/application-development/google-introduces-slsa-framework,
verified 2026-08-21), which states. "the new SLSA framework formalizes
criteria around software supply chain integrity, to help the industry
and open-source ecosystem secure the software development lifecycle."
Google drew on its own internal Binary Authorization for Borg practice
as the model. SLSA is now maintained by the Linux Foundation as a
cross-industry specification, currently at version 1.2.

The alias **Build Provenance** names the specific document this pattern
produces. **SLSA Attestation** names the broader class of signed
statement a provenance document belongs to, since SLSA also covers
other attestation types beyond provenance alone.

## 2. Problem and context

A person or a system consuming a software artifact, a compiled binary,
a container image, a published package, has no way to answer a basic
question from the artifact alone. where did this actually come from,
which source code produced it, on which build system, following which
build steps, and was that build tampered with along the way. A
malicious actor who compromises a build system, a source repository, or
a package registry can insert code into an artifact that looks
identical to the legitimate one, and nothing in the artifact itself
proves otherwise.

The consequence of this gap is well documented in real incidents where
a build pipeline, rather than the source code itself, was the point of
compromise. an attacker who controls the build gets to ship whatever
they want under a trusted name, and a consumer verifying only the
artifact's checksum or signature has no way to know the build that
produced it followed the process the source code actually describes.
SLSA provenance closes this gap by producing a signed, verifiable
record of exactly how, where, and from what an artifact was built, so a
consumer can check the record against the artifact before trusting it.

## 3. Forces

The pattern balances the following competing pressures.

- **Verifiability.** Favoured. A provenance document is a signed
  attestation a consumer can check independently, rather than a claim
  the artifact publisher simply asserts.
- **Build system trust.** Favoured, at an infrastructure cost. Higher
  SLSA levels require the build to run on a platform that generates its
  own provenance non-forgeably, which means the build infrastructure
  itself needs to be hardened and trusted, not only the code it builds.
- **Adoption friction.** Sacrificed, at the lower levels, and
  progressively recovered. SLSA is deliberately structured as
  incremental levels, so a project can adopt basic provenance
  generation cheaply and work up toward stronger guarantees rather than
  needing full infrastructure hardening from day one.
- **Ecosystem-wide consistency.** Favoured. Because SLSA is a
  cross-industry specification maintained by the Linux Foundation
  rather than one vendor's proprietary format, provenance generated by
  one build platform can, in principle, be verified by tooling built by
  an entirely different vendor.
- **Coverage of the whole supply chain.** Sacrificed, honestly.
  Provenance for the final build step says nothing, on its own, about
  the provenance of every dependency that went into that build, which
  is why the pattern is most effective paired with a Supply Chain SBOM
  covering the dependency tree.

## 4. Applicability and non-applicability

Reach for SLSA Provenance when the following hold.

- The artifact is consumed by parties who need a real answer to where
  did this come from beyond trusting the publisher's word, an internal
  platform team distributing binaries to other teams, or a public
  package a wide audience installs.
- The build pipeline can be instrumented, or already runs on a platform
  that can generate provenance for it, without requiring a from-scratch
  infrastructure rebuild to get started at the lower SLSA levels.
- The organisation has, or is building toward, a policy that gates
  deployment or installation on the presence and verification of a
  provenance attestation, since generating provenance nobody checks
  provides little real protection.

Do NOT reach for SLSA Provenance in these cases, and the reason matters
more than the rule.

- **No consumer will ever verify the attestation**, generating a
  provenance document that nothing in the deployment or installation
  pipeline actually checks produces paperwork with no real security
  benefit, and the effort is better spent making the attestation
  actually enforced before adding more of it.
- **The build environment cannot be meaningfully hardened at all**, a
  provenance document generated by a build system with no isolation and
  no non-forgeable identity only proves what the build claims about
  itself, which is close to no stronger a guarantee than the artifact
  alone offered.
- **The project's real risk is entirely in its dependency tree, not its
  own build step**, provenance for the final artifact says nothing
  about a compromised transitive dependency, which needs a Supply Chain
  SBOM and dependency-level attestation instead, or in addition.

## 5. Structure

An SLSA provenance document has three structural layers, following the
in-toto attestation format the SLSA specification recommends for its
statement layer.

- **The statement**, an in-toto attestation binding the provenance
  content to a specific artifact by its cryptographic digest, so the
  document cannot be silently reattached to a different artifact.
- **The predicate**, the provenance content itself. the build's source
  repository and commit, the build platform's identity, the exact build
  steps executed, and the parameters and dependencies the build
  consumed.
- **The envelope and signature**, wrapping the statement in a signed
  envelope so a consumer can verify both that the content has not been
  altered and that it was produced by a specific, identifiable build
  platform.

The SLSA levels describe how strongly a consumer can trust that the
predicate is accurate. higher levels require the provenance to be
generated non-forgeably by the build platform itself, rather than
supplied by the same party that controls the artifact's source.

```
    Consumer, before trusting the artifact:

    1. fetch the provenance attestation

```

## 7. Dynamics

The trace below shows a build producing provenance and a consumer
verifying it before use.

```
Build phase

CI pipeline checks out source at commit C
   |-- build platform executes the defined build steps -----> artifact A
   |
   |-- build platform generates provenance predicate --------> records
   |   (source=C, steps=..., dependencies=...)                 what happened
   |
   |-- build platform signs the statement binding -----------> signed
   |   the predicate to artifact A's digest                    provenance
   |
   |-- signed provenance published alongside artifact A

Verification phase, at consumption time

consumer downloads artifact A and its provenance
   |-- verify signature against the trusted build platform key
   |<-- signature valid, provenance was genuinely produced by
   |    the claimed build platform, not forged by a third party
   |
   |-- verify artifact A's digest matches the provenance statement's
   |   subject digest
   |<-- match confirmed, provenance describes THIS artifact
   |
   |-- check predicate against policy (source repo allowed,
   |   SLSA level meets the required threshold)
   |<-- policy satisfied, artifact accepted
```

## 8. Implementation variants

**Platform-generated provenance at build time.** The strongest variant,
where the build platform itself, not a script the build's own source
controls, generates and signs the provenance, so a compromised build
script cannot forge a clean attestation for a tampered artifact. This
is what the higher SLSA levels require.

**Post-build attestation generation.** A weaker but simpler variant,
where a separate tool inspects a completed build's metadata after the
fact and generates a provenance document from it. Easier to retrofit
onto an existing pipeline, but offers a correspondingly weaker
guarantee, since the same actor that could tamper with the build could,
in principle, also control the post-build attestation step.

**Container-image provenance via attestation-aware registries.**
Container registries and signing tools that support attaching
provenance and signature metadata directly to an image manifest, so a
pull operation can carry the provenance alongside the image itself
rather than needing a separate out-of-band lookup.

**Package-manager-integrated provenance.** Language package registries
that support publishing and displaying build provenance alongside a
package version, letting a consumer inspect the provenance from the
package listing itself before installing, without needing separate
tooling.

## 9. Known production uses

**The SLSA specification itself, maintained by the Linux Foundation.**
The v1.2 specification's provenance page defines provenance as.
"verifiable information that can be used to track an artifact back,
through all the moving parts in a complex supply chain, to where it
came from." SLSA specification, Provenance, v1.2,
https://slsa.dev/spec/v1.2/provenance, verified 2026-08-21.

**in-toto, the attestation format SLSA provenance is built on.** The
SLSA specification's attestation model page recommends in-toto
attestations as the statement-layer format every SLSA provenance
document uses, describing provenance as one specific predicate type
carried inside a signed in-toto statement. SLSA specification, Software
attestations, https://slsa.dev/attestation-model, verified 2026-08-21.

**GitHub artifact attestations, establishing build provenance for
GitHub Actions builds.** GitHub's own documentation describes generated
artifact attestations as establishing verifiable build provenance for
artifacts produced by an Actions workflow, the current built-in path
GitHub recommends for generating this class of attestation. GitHub
documentation, Using artifact attestations to establish provenance for
builds,
https://docs.github.com/en/actions/security-for-github-actions/using-artifact-attestations/using-artifact-attestations-to-establish-provenance-for-builds,
verified 2026-08-21.

## 10. Consequences

Positive.

- A consumer gets a verifiable, signed answer to where an artifact came
  from, rather than needing to trust the publisher's unverified claim.
- The incremental level structure lets a project start with basic,
  cheap provenance generation and work toward stronger, non-forgeable
  guarantees over time, rather than needing a full infrastructure
  rebuild before adopting the pattern at all.
- Being a cross-industry, vendor-neutral specification means provenance
  generated on one build platform can, at least in principle, be
  verified with tooling built by a different vendor.
- Pairing provenance with a policy that gates deployment or
  installation turns a compromised build or a tampered artifact from a
  silent risk into a blocked one.

Negative.

- Provenance for the final build step says nothing about the provenance
  of the dependencies consumed during that build, so the pattern alone
  does not close the whole supply-chain trust gap.
- Higher SLSA levels genuinely require build infrastructure hardening,
  a real and ongoing cost, not a one-time configuration change.
- Generating provenance that nothing downstream actually verifies
  produces paperwork with little real security benefit, and it is easy
  for an organisation to stop at generation without ever building the
  verification and enforcement side.
- The lower SLSA levels, while cheap to adopt, offer a correspondingly
  weaker guarantee, since a self-reported provenance document is only
  as trustworthy as the party that generated it.

## 11. Failure modes and misuse

**Generating provenance that nothing downstream ever verifies.**
Symptom. A project publishes signed provenance for every release, and
an audit later finds no deployment or installation step anywhere
actually checks it before consuming the artifact. Cause. Treating
provenance generation as the whole goal rather than the input to a
verification and policy step that actually gates on it. Fix. Build the
verification and policy enforcement side before, or at the same time
as, the generation side, and treat unverified provenance as a project
still in progress, not a completed control.

**Generating provenance at a self-reported level the build
infrastructure cannot actually back up.** Symptom. A project claims a
higher SLSA level than its build infrastructure genuinely supports, a
non-hardened, forgeable build script generating its own provenance
while the project's documentation claims a level that requires
platform-generated, non-forgeable attestation. Cause. Confusing the
provenance document's CONTENT, which can describe any level, with the
BUILD PLATFORM's actual capability to back that content non-forgeably.
Fix. Confirm the SLSA level claimed matches what the build
infrastructure can genuinely guarantee, and prefer an honest lower
level over an unearned higher one.

**Treating a valid provenance signature as proof the source code
itself is safe.** Symptom. A team accepts an artifact because its
provenance verifies cleanly, without separately reviewing whether the
source repository and commit the provenance points to were themselves
trustworthy. Cause. Provenance proves the build faithfully reflects
what the specified source and steps describe, it says nothing about
whether that source was itself malicious or compromised upstream. Fix.
Treat provenance verification as one layer among several, source review,
dependency scanning, and provenance verification together, never
provenance alone as a complete answer to artifact trust.

## 12. Trade-off matrix

Compared against named alternatives, across the forces from dimension 3.

| Force | SLSA Provenance | A plain checksum or hash | A code-signing certificate alone | A Supply Chain SBOM alone |
|---|---|---|---|---|
| Answers where did this come from | Yes, with build and source detail | No, only confirms bit-for-bit identity | Partially, confirms publisher identity only | Partially, lists components, not the build process |
| Verifiable independently of the publisher | Yes, at the higher levels | Yes, but proves nothing about origin | Yes, proves signer identity only | Depends on how it was generated |
| Covers the build process itself | Yes | No | No | No |
| Covers the dependency tree | No, needs pairing with an SBOM | No | No | Yes, that is its purpose |
| Adoption cost | Low to start, real at higher levels | Minimal | Moderate, needs a signing infrastructure | Moderate, needs dependency tooling |

Reading of the table. SLSA Provenance wins when the question is
specifically how and where an artifact was built, and a signed,
verifiable answer to that question matters. A plain checksum only
proves an artifact has not changed since it was hashed, nothing about
its origin. A code-signing certificate proves who published an
artifact, not how it was built or from what. A Supply Chain SBOM
answers a complementary question, what is inside the artifact, and the
two patterns are strongest paired together rather than as substitutes
for one another.

## 13. Related and incompatible patterns

- **Supply Chain SBOM.** The complementary pattern covering the
  dependency tree that provenance for the final build step does not
  reach on its own. the strongest supply-chain posture pairs both.
- **Sigstore Signing.** A widely used signing infrastructure that can
  carry an SLSA provenance attestation's signature, providing the
  cryptographic identity layer the provenance envelope depends on.
- **Immutable Infrastructure.** A build platform built on immutable,
  reproducible infrastructure is a natural fit for generating the
  non-forgeable provenance the higher SLSA levels require.
- **Zero Trust Architecture.** SLSA provenance is one concrete
  mechanism for realising a zero-trust principle, verify explicitly,
  at the software supply chain layer specifically, rather than trusting
  an artifact by default because of where it arrived from.
- **Unattested third-party artifacts.** Conflicts directly. accepting
  an artifact with no provenance, or with provenance nobody checks,
  while claiming to follow SLSA-informed policy, defeats the entire
  point the pattern exists to serve.

## 14. Refactoring path in and out

Introducing the pattern into a pipeline that does not have it. Ordered
steps, following SLSA's own incremental-level structure.

1. Confirm the build is already scripted and version-controlled, the
   baseline the lowest SLSA level assumes, rather than a manual or
   undocumented build process.
2. Generate a basic provenance document describing the build's source
   commit, build steps, and parameters, even before the build platform
   itself can generate it non-forgeably.
3. Move provenance generation onto the build platform itself, so the
   party controlling the artifact's source cannot also forge the
   provenance describing how it was built.
4. Harden the build platform's own identity and isolation to the point
   it can generate provenance non-forgeably, meeting the higher SLSA
   levels the project's risk profile calls for.
5. Add a verification and policy step at deployment or installation
   time that actually checks the provenance before accepting an
   artifact, closing the loop the first failure mode in dimension 11
   warns against leaving open.

Removing the pattern when it stops earning its place. Signals that it
should go include a project whose provenance generation has never been
paired with any downstream verification, or one whose real supply-chain
risk sits entirely in a dependency tree that provenance for the final
build step never reaches.

1. Confirm whether anything downstream actually verifies the generated
   provenance. if nothing does, the generation step is unearned
   overhead until verification is built.
2. Confirm whether the project's actual risk profile is better served
   by investing in dependency-level attestation and a Supply Chain
   SBOM instead.
3. If provenance generation is removed, document plainly that the
   project no longer makes this specific claim, rather than leaving a
   stale or unmaintained attestation in place that a consumer might
   still trust.

## 15. Testing and verification

Easier because of the pattern.

- A provenance document is a structured, machine-checkable artifact, so
  verifying it against policy is a straightforward automated step
  rather than a manual review.
- Because the statement binds the predicate to a specific artifact
  digest, a test can construct a mismatched artifact and confirm
  verification correctly rejects it, proving the binding is enforced
  rather than merely documented.
- The incremental level structure gives a natural test matrix, confirm
  the pipeline actually meets the level it claims by checking each
  level's specific requirement, scripted and version-controlled build,
  platform-generated provenance, isolated build environment, and so on.

Harder because of the pattern.

- Testing that a build platform genuinely cannot forge provenance
  describing a build it did not perform needs a real adversarial test
  against the platform's isolation, not only a check that a document
  with the right fields exists.
- Verifying provenance end to end, from build through publication
  through consumer-side policy enforcement, needs the whole pipeline
  wired together, which is a larger integration test than most
  unit-level checks cover.

Techniques that apply.

- **Digest-mismatch rejection test.** Construct a provenance document
  whose subject digest does not match the artifact under test, and
  assert the verification step rejects it.
- **Signature-tamper rejection test.** Alter a signed provenance
  document after signing and assert verification rejects the altered
  copy.
- **Level-requirement test matrix.** For each SLSA level the project
  claims, assert the specific requirement that level demands is
  actually met by the pipeline, rather than only that a provenance
  document with the right label exists.
- **Policy-enforcement integration test.** Confirm a deployment or
  installation step genuinely refuses an artifact with missing,
  invalid, or policy-violating provenance, closing the loop the first
  failure mode in dimension 11 describes.

## 16. Observability signals

What to record.

- The count of artifacts published with valid, verified provenance
  against the count published without it, tracked over time, as the
  direct measure of how completely the pattern has actually been
  adopted across the project's real release surface.
- The count of provenance verification failures at consumption time,
  broken down by cause, digest mismatch, signature failure, or policy
  violation, since each cause points at a different part of the
  pipeline to investigate.

A healthy state. Every published artifact carries valid provenance,
verification runs automatically at every consumption point, and
verification failures are rare and, when they occur, are investigated
rather than silently bypassed.

A failing state. Provenance is generated for some artifacts but not
others with no clear reason why, verification exists in tooling but is
not actually wired into the deployment or installation path, or
verification failures are routinely overridden rather than treated as
a signal something upstream needs attention.

## 17. Security and privacy implications

SLSA Provenance is itself a security control, so its main
implications are about what it does and does not actually guarantee,
and about the metadata it exposes.

**Provenance content can reveal internal build infrastructure
details.** A provenance predicate describes the build platform, the
build steps, and the dependencies consumed, which is exactly the
information a consumer needs to verify the artifact, but which can also
reveal internal infrastructure names, paths, or configuration to anyone
who can read the published attestation. Review what a provenance
document exposes before publishing it alongside a public artifact,
the same way any other public metadata is reviewed.

**A valid signature only proves what it claims to prove, not artifact
safety.** Verified provenance proves the artifact was built by the
claimed platform from the claimed source, following the claimed steps.
It says nothing about whether that source was itself free of
vulnerabilities or malicious code, which is why provenance verification
is one layer in a defence, source review, dependency scanning, and
provenance verification together, never a single, sufficient check on
its own.

## Code examples

Three languages, each showing a minimal in-toto-shaped provenance
predicate and a verification check confirming the artifact's digest
matches the statement's subject. These examples model the SHAPE of
provenance generation and verification. a real deployment uses a
signing library and a trusted key, which this entry keeps out of scope
so the shape stays clear. TypeScript builds and checks a provenance
object directly. Python does the same, computing a real SHA-256 digest
over sample artifact bytes to demonstrate the binding. Swift shows the
same predicate shape and digest check using Foundation's cryptography
support. Java and Go are omitted, because a faithful minimal example
needs either a real in-toto library import or enough manual JSON and
digest handling that it would collapse into boilerplate rather than
demonstrating the pattern's actual shape. Rust is omitted for the same
space reason noted elsewhere in this family.

### TypeScript

```typescript
import { createHash } from "crypto";

interface Provenance {
  subjectDigest: string;
  sourceRepo: string;
  sourceCommit: string;
  buildPlatform: string;
}

function digestOf(artifact: Buffer): string {
  return createHash("sha256").update(artifact).digest("hex");
}

function verify(artifact: Buffer, provenance: Provenance): boolean {
  return digestOf(artifact) === provenance.subjectDigest;
}

const artifact = Buffer.from("sample-artifact-bytes");
const provenance: Provenance = {
  subjectDigest: digestOf(artifact),
  sourceRepo: "github.com/example/project",
  sourceCommit: "abc1234",
  buildPlatform: "ci.example.com",
};

console.log(verify(artifact, provenance));
```

### Python

```python
import hashlib
from dataclasses import dataclass


@dataclass(frozen=True)
class Provenance:
    subject_digest: str
    source_repo: str
    source_commit: str
    build_platform: str


def digest_of(artifact: bytes) -> str:
    return hashlib.sha256(artifact).hexdigest()


def verify(artifact: bytes, provenance: Provenance) -> bool:
    return digest_of(artifact) == provenance.subject_digest


if __name__ == "__main__":
    artifact = b"sample-artifact-bytes"
    provenance = Provenance(
        subject_digest=digest_of(artifact),
        source_repo="github.com/example/project",
        source_commit="abc1234",
        build_platform="ci.example.com",
    )
    print(verify(artifact, provenance))
```

### Swift

```swift
import Foundation
import Crypto

struct Provenance {
    let subjectDigest: String
    let sourceRepo: String
    let sourceCommit: String
    let buildPlatform: String
}

func digest(of artifact: Data) -> String {
    SHA256.hash(data: artifact).map { String(format: "%02x", $0) }.joined()
}

func verify(_ artifact: Data, against provenance: Provenance) -> Bool {
    digest(of: artifact) == provenance.subjectDigest
}

let artifact = Data("sample-artifact-bytes".utf8)
let provenance = Provenance(
    subjectDigest: digest(of: artifact),
    sourceRepo: "github.com/example/project",
    sourceCommit: "abc1234",
    buildPlatform: "ci.example.com"
)

print(verify(artifact, against: provenance))
```
