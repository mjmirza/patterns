# Audit Log

## 1. Name, aliases, and lineage

The canonical name in this entry is Audit Log. Common aliases are Audit Trail,
Security Audit Log, Activity Log, and Event Audit Trail. Product documents vary
by domain. Kubernetes calls the feature auditing and describes it as a
security-relevant chronological record of cluster actions
([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
verified 2026-08-02). GitHub Enterprise Cloud calls its facility the audit log
and names entries by event category plus operation type
([GitHub Docs, "Audit log for an enterprise"](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise),
verified 2026-08-02). Google Cloud uses Cloud Audit Logs for records that help
answer who did what, where, and when in Google Cloud resources
([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
verified 2026-08-02). AWS CloudTrail presents the same idea as account activity
visibility over AWS infrastructure
([AWS CloudTrail User Guide, "What Is AWS CloudTrail?"](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html),
verified 2026-08-02).

This pattern is older than object-oriented pattern catalogs. It comes from
audit, accounting, operating system security, and incident response practice,
not from a single design-pattern book. NIST SP 800-92, Karen Kent and Murugiah
Souppaya, *Guide to Computer Security Log Management*, September 2006, frames
computer security log management as enterprise practice and places it in the
Audit and Accountability control family
([NIST SP 800-92 landing page](https://csrc.nist.gov/pubs/sp/800/92/final),
verified 2026-08-02). OWASP's Logging Cheat Sheet distinguishes audit trails
from general application logging and says audit trails support reconstruction,
review, and examination of attributable transactions
([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
verified 2026-08-02).

This entry treats Audit Log as an architectural pattern. The pattern is not
"write more logs". It is the deliberate recording of security-relevant,
business-relevant, and accountability-relevant events as append-only records
with stable identity, time, actor, action, target, result, and correlation
fields. General diagnostic logging tells an engineer why code failed. An audit
log tells an investigator, reviewer, customer, or regulator what happened and
who or what initiated it.

## 2. Problem and context

A system accepts actions whose history must survive beyond the request that
performed them. A user grants access to a repository. A cloud principal changes
a policy. A cluster controller deletes a secret. A billing admin exports
customer records. A service account rotates a key. If the only record is the
current database state, the system cannot later explain how that state came to
exist. If the only record is a debug line mixed with stack traces and cache
misses, the record is hard to search, hard to retain, and weak as evidence.

The pattern addresses the gap between authorization and accountability. Access
control decides whether an operation may happen. The audit log records that the
operation was attempted, by which actor, against which target, with which
result, under which request context. Kubernetes states that audit records
document the sequence of actions generated by users, applications that use the
Kubernetes API, and the control plane itself
([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
verified 2026-08-02). GitHub Enterprise audit entries include actor,
repository, action, date and time, identity data, authentication method for
non-UI actions, and optional source IP address
([GitHub Docs, "Audit log for an enterprise"](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise),
verified 2026-08-02). OWASP recommends event attributes that cover when,
where, who, and what, plus action, object, result status, reason, and request
context where applicable
([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
verified 2026-08-02).

The context that makes the pattern fit has five parts. First, the system has
events that matter after the user interface has moved on. Second, the event can
be named in domain language. Third, the actor can be identified as a human,
service, job, token, or anonymous subject with a stable request identity.
Fourth, the target can be named without leaking more data than the audit reader
is allowed to see. Fifth, there is a retention and review path. An audit log
that nobody can query, preserve, or interpret is storage cost, not
accountability.

Engineering judgement: the best audit logs are written close to the policy or
state boundary. Logging from the UI misses API calls. Logging from a background
worker misses the person who requested the job unless the request context is
carried into the job. Logging in the database sees the final write but often
loses the business action that caused it. Place the pattern where the system
still knows actor, action, target, authorization decision, and result.

## 3. Forces

Engineering judgement: this dimension weighs design pressure. Citations in
this section identify real mechanisms; the balance described here is a design
reading.

- **Coupling.** Favoured when business code emits a small audit event contract
  rather than formatting log files. Sacrificed because each protected workflow
  now depends on audit vocabulary and a sink.
- **Consistency.** Favoured when events share required fields and event names.
  Sacrificed when every team invents `userId`, `uid`, `actor`, and `principal`
  for the same value.
- **Latency.** Sacrificed if the request waits on a remote sink. Favoured when
  audit writes are buffered without dropping on success paths. Kubernetes notes
  that audit logging increases API server memory because request context is
  stored for auditing
  ([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
  verified 2026-08-02).
- **Operability.** Favoured because responders can query who, what, where, and
  when. Sacrificed if high-cardinality labels, secret fields, or noisy event
  classes flood the pipeline.
- **Cost.** Sacrificed through storage, indexing, retention, export, and
  review. Google Cloud says Data Access audit logs can be large and may add
  logging charges when enabled
  ([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
  verified 2026-08-02).
- **Team topology.** Favoured when a platform team owns the event schema and
  product teams own domain event coverage. Sacrificed when central approval is
  required for every event name.
- **Cognitive load.** Sacrificed. Developers must decide which event belongs in
  the audit stream, which fields are safe, and whether the event records an
  attempt, a decision, a state change, or a completed side effect.
- **Evidence quality.** Favoured when records are immutable, ordered, and tied
  to stable identities. Google Cloud states that Cloud Audit Logs entries are
  immutable
  ([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
  verified 2026-08-02). Sacrificed when shared accounts, clock drift, or mutable
  storage weaken attribution.
- **Privacy.** Mixed. Audit logs help detect misuse of data, but the logs can
  themselves contain sensitive data. OWASP lists data to exclude from logs,
  including secrets and sensitive personal data
  ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
  verified 2026-08-02).

The pattern favours accountability, incident response, compliance review, and
forensic reconstruction. It sacrifices local simplicity, storage cost, and some
privacy margin unless the schema is strict.

## 4. Applicability and non-applicability

Reach for Audit Log when these conditions hold.

- **Privileged actions exist.** User administration, role changes, key
  rotation, policy edits, data exports, break-glass access, and destructive
  operations need attributable records. OWASP includes user administration,
  administrative privilege use, sensitive data access, cryptographic key
  activity, system object creation or deletion, and data import or export in
  event classes to record
  ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
  verified 2026-08-02).
- **A later reader must reconstruct a sequence.** CloudTrail says account
  activity can be viewed, searched, downloaded, archived, analyzed, and used to
  identify who or what acted on which resources and when
  ([AWS CloudTrail User Guide, "What Is AWS CloudTrail?"](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html),
  verified 2026-08-02).
- **The system has multiple entry points.** UI, API, CLI, background job, and
  webhook paths need one event contract so the audit history is not biased
  toward one interface.
- **External review is part of operations.** Security teams, auditors, tenant
  admins, and customer-support reviewers need stable event names, filters, and
  export.
- **The event carries business meaning.** A record such as
  `invoice.approved` says more than a database row update. The audit reader
  needs intent and result, not only storage mutation.
- **The protected system is multi-tenant.** Audit records must separate tenant
  scope, actor identity, target identity, and administrative scope so one
  tenant cannot infer another tenant's actions.
- **The platform offers native audit hooks.** Kubernetes has policy and backend
  support for API server audit events
  ([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
  verified 2026-08-02). Google Cloud, AWS, GitHub, and Azure expose managed
  activity or audit facilities for their control planes
  ([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
  [AWS CloudTrail User Guide, "What Is AWS CloudTrail?"](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html),
  [GitHub Docs, "Audit log for an enterprise"](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise),
  [Microsoft Learn, "Activity Log in Azure Monitor"](https://learn.microsoft.com/en-us/azure/azure-monitor/platform/activity-log),
  verified 2026-08-02).

Non-applicability list.

- **The data is purely diagnostic.** Cache hit rates, SQL timings, stack traces,
  garbage collection pauses, and retry counters belong in diagnostic logs,
  traces, and metrics. Mixing them into the audit stream makes review harder.
- **The event cannot be tied to a stable actor.** Shared administrator
  accounts, unsigned headers, and anonymous batch jobs produce weak evidence.
  Fix identity first, then audit.
- **The target cannot be named without leaking restricted data.** If a record
  identifier itself reveals medical, legal, or customer-sensitive facts, use an
  opaque target identifier and protected lookup rather than raw values.
- **The event volume is machine telemetry.** Per-packet, per-sensor, per-token,
  and per-cache events can drown the audit store. Sample or aggregate in
  telemetry, and audit only decisions and security-relevant state changes.
- **The required record is an append-only business ledger.** Audit logs describe
  actions. Financial balances, inventory movements, and domain facts may need
  Event Sourcing or a ledger with domain replay semantics.
- **The main need is alerting.** Audit logs can feed alerts, but alerting alone
  does not need long retention, legal hold, or reviewer-facing query tools.
- **The system cannot protect the log.** A local file writable by the same code
  that performs the action is a weak audit record. Use remote append, restricted
  writer permissions, or storage controls before relying on it.
- **The organization will never review or retain it.** Recording events without
  a review, retention, and deletion policy creates privacy and cost without a
  matching accountability gain.
- **The product must hide all action history from the operator.** Some
  end-to-end encrypted products may choose to minimize server-side audit
  details. In that case, audit only server-visible control-plane events and be
  explicit about what is not visible.

## 5. Structure

The pattern has seven participants, named by responsibility.

- **Audited Operation.** The command, API handler, policy decision, job step, or
  state transition that creates an audit-worthy event.
- **Actor Context.** The authenticated principal, service identity, token,
  delegation chain, tenant, source address, and request identifier known at the
  time of the operation.
- **Target Descriptor.** The resource identity and class affected by the action.
  It uses stable identifiers and avoids secret or high-sensitivity values.
- **Audit Event.** The immutable record shape. At minimum it carries event time,
  observed time if different, actor, action, target, outcome, reason, request
  id, source, schema version, and event id.
- **Audit Policy.** Rules that decide which event classes are recorded and at
  which detail level. Kubernetes has policy levels such as metadata, request,
  and request plus response
  ([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
  verified 2026-08-02).
- **Audit Sink.** The append path. It can be a local file, database table,
  queue, stream, object store, logging service, or SIEM input. OWASP names file
  systems, databases, and remote collection systems as recording options
  ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
  verified 2026-08-02).
- **Reviewer and Retention Process.** The human or automated consumer that
  searches, exports, alerts, preserves, redacts, and deletes records according
  to policy.

The key relationship is directional. The Audited Operation emits Audit Events
through a narrow interface. The Audit Sink persists them in append form. The
Reviewer reads through query and export paths with permissions that are not the
same as write permissions. The operation must not be able to rewrite history
after the event is accepted by the sink.

## 7. Dynamics

The runtime flow has one core rule. Record the audit event at the point where
the system knows both the intent and the result. For a denied authorization
attempt, that may be the policy decision. For a state change, that is often
after the write commits. For an asynchronous job, the request event and job
completion event may be separate records tied by one request id.

```
Client       API/Command       Policy/Store       Audit Policy      Audit Sink
  |              |                  |                   |                |
  |-- request -->|                  |                   |                |
  |              |-- authorize ---->|                   |                |
  |              |<-- allow/deny ---|                   |                |
  |              |                  |                   |                |
  |              |-- mutate state ->|                   |                |
  |              |<-- result -------|                   |                |
  |              |                  |                   |                |
  |              |-- build event ---------------------->|                |
  |              |                  |                   |-- accept? ---->|
  |              |                  |                   |<-- yes --------|
  |              |-- append event ------------------------------------->|
  |              |<-- append ack ---------------------------------------|
  |<-- response -|                  |                   |                |

Failure branch:

  If append fails after a high-risk operation, choose fail-closed,
  queue-with-durable-spool, or incident flag by event class.
```

Four timing choices matter.

First, log attempts as well as completions where policy violations matter.
Authorization failures and input validation failures often reveal attack or
abuse even when no state changed. OWASP includes authentication success and
failure, authorization failures, session management failures, and validation
failures in events to record
([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
verified 2026-08-02).

Second, place a durable boundary before telling the caller a privileged change
has finished, or make the fallback explicit. A system that reports success and
then loses the audit event has created an attribution gap.

Third, carry correlation identifiers across queues and workers. Otherwise a
human request and the delayed job it triggered become separate stories.

Fourth, treat event time and log receipt time as different fields when clients
or edge devices can be offline. OWASP distinguishes event time from log time in
its event attribute guidance
([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
verified 2026-08-02).

## 8. Implementation variants

**Inline append in the transaction.** The domain write and audit insert happen
in the same database transaction. This variant gives strong local consistency
for monoliths and database-backed services. The trade-off is coupling to one
store and the risk that audit access shares the same compromise boundary as
business data.

**Transactional outbox.** The operation writes an audit event to an outbox table
with the domain change, and a relay publishes it to the audit sink. This
preserves the event when the external sink is down and avoids blocking the
request on a remote system. The trade-off is delayed visibility and duplicate
delivery handling.

**Synchronous remote sink.** The operation sends the event to a logging service
or SIEM before returning. This gives quick central visibility. The trade-off is
request latency and a hard decision when the sink is unavailable.

**Local append with collector.** The service writes structured lines to a local
file or standard output and an agent ships them. This fits container and host
logging stacks. The trade-off is local tamper risk and backpressure behaviour
that must be known.

**Platform-native audit hook.** The control plane emits events. Kubernetes API
server auditing, AWS CloudTrail, Google Cloud Audit Logs, Azure Activity Log,
and GitHub Enterprise audit logs are examples verified in dimension 9. This
variant gives broad coverage for the platform boundary. The trade-off is that
domain-level intent inside an application may still be absent.

**Database trigger audit.** A trigger records row changes. This captures writes
no matter which app path touched the table. The trade-off is loss of business
intent unless actor and request context are passed into the database session.

**Event-sourced domain log.** The domain event stream doubles as the audit
source. This is attractive when domain events already name actor, command,
target, and result. The trade-off is that privacy redaction, retention, and
legal hold may diverge from domain replay needs.

**Cryptographic chain.** Each event includes a hash of the previous event or is
sealed by a signing service. This helps detect deletion or reordering in a
store the application can read. The trade-off is key handling, rotation,
recovery from gaps, and batch verification cost.

The following minimal examples use a small event contract and append to a
memory sink. They were run on 2026-08-20 with `npx tsc` plus `node`, `python3`,
and `go run`.

TypeScript.

```typescript
type AuditOutcome = "allow" | "deny";

type AuditEvent = Readonly<{
  at: string;
  actor: string;
  action: string;
  target: string;
  outcome: AuditOutcome;
  requestId: string;
}>;

class MemoryAuditSink {
  private readonly events: AuditEvent[] = [];

  append(event: AuditEvent): void {
    this.events.push(Object.freeze(event));
  }

  all(): readonly AuditEvent[] {
    return this.events;
  }
}

function recordAudit(
  sink: MemoryAuditSink,
  actor: string,
  action: string,
  target: string,
  outcome: AuditOutcome,
  requestId: string
): void {
  sink.append({
    at: new Date(0).toISOString(),
    actor,
    action,
    target,
    outcome,
    requestId,
  });
}

const sink = new MemoryAuditSink();
recordAudit(sink, "user-42", "invoice.approve", "invoice-7", "allow", "req-1");
console.log(JSON.stringify(sink.all()));
```

Python.

```python
from dataclasses import asdict, dataclass
from datetime import datetime, timezone
import json


@dataclass(frozen=True)
class AuditEvent:
    at: str
    actor: str
    action: str
    target: str
    outcome: str
    request_id: str


class AuditSink:
    def __init__(self):
        self.events = []

    def append(self, event: AuditEvent):
        self.events.append(event)


def record_audit(sink, actor, action, target, outcome, request_id):
    event = AuditEvent(
        at=datetime.fromtimestamp(0, timezone.utc).isoformat(),
        actor=actor,
        action=action,
        target=target,
        outcome=outcome,
        request_id=request_id,
    )
    sink.append(event)


sink = AuditSink()
record_audit(sink, "user-42", "invoice.approve", "invoice-7", "allow", "req-1")
print(json.dumps([asdict(event) for event in sink.events]))
```

Go.

```go
package main

import (
	"encoding/json"
	"fmt"
	"time"
)

type AuditEvent struct {
	At        string `json:"at"`
	Actor     string `json:"actor"`
	Action    string `json:"action"`
	Target    string `json:"target"`
	Outcome   string `json:"outcome"`
	RequestID string `json:"request_id"`
}

type AuditSink struct {
	events []AuditEvent
}

func (s *AuditSink) Append(event AuditEvent) {
	s.events = append(s.events, event)
}

func RecordAudit(sink *AuditSink, actor, action string,
	target string, outcome string, requestID string) {
	sink.Append(AuditEvent{
		At:        time.Unix(0, 0).UTC().Format(time.RFC3339),
		Actor:     actor,
		Action:    action,
		Target:    target,
		Outcome:   outcome,
		RequestID: requestID,
	})
}

func main() {
	sink := &AuditSink{}
	RecordAudit(sink, "user-42", "invoice.approve", "invoice-7", "allow", "req-1")
	data, err := json.Marshal(sink.events)
	if err != nil {
		panic(err)
	}
	fmt.Println(string(data))
}
```

## 9. Known production uses

**AWS CloudTrail.** AWS CloudTrail records AWS account activity. AWS states that
CloudTrail can be used to view, search, download, archive, analyze, and respond
to account activity, and to identify who or what took an action, which
resources were acted on, and when the event occurred
([AWS CloudTrail User Guide, "What Is AWS CloudTrail?"](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-user-guide.html),
verified 2026-08-02). The CloudTrail log file examples show event records with
fields such as event time, event source, event name, user identity, source IP
address, user agent, request parameters, response elements, and request id
([AWS CloudTrail User Guide, "CloudTrail log file examples"](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-examples.html),
verified 2026-08-02).

**Kubernetes API server auditing.** Kubernetes auditing records a chronological
set of security-relevant cluster actions from users, API clients, and the
control plane. Audit events begin in the `kube-apiserver`, are processed by a
policy, and are written to backends such as log files and webhooks
([Kubernetes, "Auditing"](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/),
verified 2026-08-02).

**GitHub Enterprise Cloud audit log.** GitHub Enterprise Cloud provides an
enterprise audit log whose entries include actor, affected user, repository,
action, country, date and time, SAML SSO and SCIM identity where applicable,
authentication method for non-UI actions, and optional source IP address
([GitHub Docs, "Audit log for an enterprise"](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise),
verified 2026-08-02). GitHub also exposes search, export, streaming, token
event identification, IP display, and an audit log API from the same audit-log
feature set
([GitHub Docs, "Audit log for an enterprise"](https://docs.github.com/en/enterprise-cloud@latest/admin/concepts/security-and-compliance/audit-log-for-an-enterprise),
verified 2026-08-02).

**Google Cloud Audit Logs.** Google Cloud services write audit logs for
administrative activity and access within Google Cloud resources. The service
groups audit logs into Admin Activity, Data Access, System Event, and Policy
Denied classes, and states that audit log entries are immutable
([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
verified 2026-08-02).

**Azure Activity Log.** Azure Monitor Activity Log is a platform log that gives
insight into subscription-level events and includes records such as resource
modification and service health events
([Microsoft Learn, "Activity Log in Azure Monitor"](https://learn.microsoft.com/en-us/azure/azure-monitor/platform/activity-log),
verified 2026-08-02).

## 10. Consequences

Positive.

- Investigators can reconstruct high-risk actions without replaying database
  backups or reading source code.
- Reviewers can ask domain questions, such as who exported a report, who
  changed a role, or which token changed a setting.
- Access-control failures become visible. Denied attempts can reveal guessing,
  stale automation, or privilege probing.
- The event contract creates shared vocabulary between product, security,
  support, and compliance teams.
- Central sinks let multiple services contribute one timeline when request ids
  are carried through the system.
- Append-only handling limits the ability of the actor who performed an action
  to later rewrite the record.
- Query and export paths make customer-facing or regulator-facing review
  possible without opening production databases.

Negative.

- Every protected workflow now has another contract to keep current.
- Storage and indexing cost can grow fast, especially for read-heavy Data
  Access events.
- Sensitive values can leak into logs if event schemas accept free-form text.
- A synchronous sink can turn logging trouble into user-visible latency or
  outages.
- An asynchronous sink can create a window where the action has happened but
  the central audit store has not received the record.
- Debug log habits can damage audit value. Stack traces, partial objects, and
  vague messages do not answer who, what, when, target, and result.
- Retention, deletion, legal hold, and privacy requests become operational work.
- Audit fields can create false confidence when actor identity, clocks, or
  source addresses are weak.

## 11. Failure modes and misuse

Engineering judgement: these are practice-derived failure patterns. The
symptoms are phrased as observable production signals.

**Missing event on denied access.** Symptom. Security review finds successful
admin changes but no record of repeated failed attempts against the same
resource. Cause. Code logs only after a state change, so denials disappear.
Fix. Emit separate `attempted` or `denied` events at the policy decision point
for configured high-risk actions.

**Debug log mistaken for audit log.** Symptom. Reviewers search for
`role.grant` and find only request paths, stack traces, and text messages with
inconsistent actor fields. Cause. Diagnostic logging is used as the audit
record. Fix. Add a typed audit event contract and keep diagnostic logs separate
from audit records.

**Shared actor identity.** Symptom. Hundreds of privileged events show
`admin` or `svc-prod` as actor, and nobody can tie an event to a person or
caller. Cause. Shared accounts or missing delegation context. Fix. Require
named identities, record delegated actor chains, and block shared privileged
paths except break-glass flows that create their own event.

**Sensitive field spill.** Symptom. A log search returns tokens, passwords,
full request bodies, payment data, or personal data unrelated to review. Cause.
Free-form payload logging or high-detail policy on sensitive endpoints. Fix.
Use allowlisted fields, redaction at the event builder, and schema tests that
reject banned keys.

**Mutable audit store.** Symptom. An operator can edit or delete records with
the same role used to run the application. Cause. Audit records are stored in a
normal table or file under broad write permissions. Fix. Separate writer and
reader roles, use append-only storage where available, route to a remote sink,
and alert on deletion or retention-policy edits.

**Audit sink blocks the product.** Symptom. Login, checkout, or admin pages
slow down whenever the logging service is slow. Cause. Synchronous append on
all event classes with no timeout or spool. Fix. Classify events by risk. Use
short timeouts, durable local queueing, and fail-closed only where the policy
requires it.

**Dropped asynchronous events.** Symptom. Event counters at services exceed
events received by the central sink, but no user error occurred. Cause.
In-memory queues, process restarts, or collector backpressure. Fix. Use a
durable spool, sequence numbers, delivery metrics, and reconciliation jobs.

**Noisy audit class.** Symptom. Review tools show millions of low-risk reads
and hide rare privileged writes. Cause. The audit policy records broad read
traffic at high detail. Fix. Split event classes and retention. Keep high-risk
events searchable longer and lower-detail high-volume events in cheaper
storage.

**Clock and ordering confusion.** Symptom. The same request appears to complete
before it starts, or events from two regions cannot be ordered. Cause. Clock
skew and a single timestamp field. Fix. Record event time, receipt time,
monotonic sequence where possible, region, and request id.

**Schema drift.** Symptom. Dashboards break after one service renames `target`
to `resource` or changes outcome values. Cause. Audit events are plain maps
without versioned schema. Fix. Version the event schema, test producers, and
run compatibility checks in CI.

## 12. Trade-off matrix

Compared against named alternatives, across the forces from dimension 3.

| Force | Audit Log | Diagnostic Logging | Event Sourcing | Change Data Capture | Metrics | Distributed Tracing |
|---|---|---|---|---|---|---|
| Main question | Who did what, to what, when, and result | Why code behaved that way | What domain facts happened | Which rows changed | How much and how fast | Where a request spent time |
| Coupling | Medium. Code emits event contract | Low. Text can be local | High. Domain model is event-based | Low to app, high to schema | Low | Medium through context |
| Evidence quality | High if identity and storage hold | Low to medium | High for domain facts | Medium. Intent can be missing | Low | Low for accountability |
| Latency | Depends on sink and policy | Usually low | Can be on write path | Usually off path | Low | Low to medium |
| Storage cost | Medium to high | Medium | High, domain lifetime | High for busy tables | Low | Medium |
| Privacy risk | High if fields are loose | High if payloads leak | High, long-lived facts | High, raw data changes | Low | Medium |
| Reconstruct sequence | Strong for selected actions | Weak | Strong for domain state | Strong for row changes | Weak | Strong per request only |
| Reviewer use | Strong with query/export | Weak | Requires domain knowledge | Requires schema knowledge | Weak | Weak |
| Team ownership | Platform schema plus product events | Local teams | Domain teams | Data platform teams | Service owners | Platform plus service owners |
| Best fit | Accountability and review | Debugging | Domain state replay | Data replication and forensics | Alerting and capacity | Latency and dependency analysis |

Reading of the table. Audit Log wins when attribution and later review are the
job. Diagnostic logging wins when engineers need failure detail. Event Sourcing
wins when the business model is event history. Change Data Capture wins when
the database is the source of truth and the app cannot emit events. Metrics win
when the question is aggregate health. Tracing wins when the question is
request path and latency.

## 13. Related and incompatible patterns

- **Complete Mediation.** Composes with Audit Log. The mediation point sees
  every protected access and is the best place to record attempt, decision, and
  target.
- **Least Privilege.** Composes with Audit Log. Audit data reveals standing
  access that is unused or overbroad, while least privilege reduces the blast
  radius when an audited actor is compromised.
- **RBAC and ABAC.** Feed Audit Log. RBAC gives role context, ABAC gives
  attribute and policy context. The audit event should record enough decision
  context to explain an allow or deny without exposing sensitive policy data.
- **Zero Trust.** Composes with Audit Log. Continuous verification needs
  evidence of actor, device, network, policy decision, and target across
  boundaries.
- **Separation of Duties.** Uses Audit Log as evidence. If one person must not
  both request and approve, the audit stream is where reviewers detect the same
  actor or delegated chain on both sides.
- **Event Sourcing.** Can replace or feed Audit Log. Domain events may satisfy
  audit needs if they contain actor, target, result, and retention controls.
  They do not replace platform audit events by default.
- **Change Data Capture.** Complements Audit Log. CDC captures database
  mutation after the fact. Audit Log captures intent and actor at the service
  boundary.
- **Immutable Ledger.** A stronger storage pattern for some audit records.
  Ledger storage adds tamper evidence and strict ordering, but costs more and
  may be poor for high-volume low-risk events.
- **Unstructured Logging.** Conflicts when used as the sole audit record.
  Free-form messages resist stable queries, retention classes, field access
  control, and schema tests.
- **Shared Accounting.** Conflicts. A shared actor collapses attribution and
  makes the audit record weak even if all other fields are present.

## 14. Refactoring path in and out

Introducing the pattern into code that does not have it.

1. Name the protected actions in business terms. Start with a small list:
   role changes, user administration, token creation, data export, destructive
   writes, break-glass access, and configuration edits.
2. Define one event schema with required fields: schema version, event id,
   event time, observed time, actor, action, target, outcome, reason, request
   id, source, tenant, and detail map.
3. Create an `AuditSink` interface and a test sink. Keep formatting and
   transport behind the sink so handlers do not know storage details.
4. Add event builders at policy or state boundaries. Use Extract Function where
   the handler currently intermixes authorization, mutation, and log text. See
   the refactoring family entry on Extract Function.
5. Add tests for one action. Assert that allow, deny, and failure paths emit
   expected event names and safe fields.
6. Route the sink to durable storage. For monoliths, start with same-transaction
   insert or transactional outbox. For distributed systems, choose a queue,
   stream, or managed logging facility.
7. Add field allowlists and redaction tests before broad rollout.
8. Add query views and reviewer permissions. Write access and read access are
   separate duties.
9. Backfill only when the old data is reliable. Do not invent actors or event
   times from weak diagnostic lines.
10. Expand by action class, not by service count. This keeps event vocabulary
   coherent.

Removing the pattern when it stops earning its place.

1. Confirm the event class has no reviewer, alert, compliance, customer, or
   incident-response use.
2. Measure query volume and retention obligations before deletion.
3. Lower detail first. Move from request bodies to metadata, or from every read
   to privileged reads.
4. Shorten retention for the event class if policy allows.
5. Replace audit records with metrics or diagnostic logs only when the question
   is aggregate health or debug detail, not accountability.
6. Remove producer code after consumers and retention rules are changed.
7. Keep schema documentation that marks the event as retired so old records
   remain interpretable.

## 15. Testing and verification

Engineering judgement: testing an audit log is less about checking that a
logger was called and more about proving that the accountability contract holds
on every important path.

Easier because of the pattern.

- A typed event contract gives tests a stable object to assert.
- A test sink can capture events without reading files.
- Authorization tests can assert both decision and audit evidence.
- Schema tests can block sensitive keys before the event reaches storage.

Harder because of the pattern.

- Asynchronous sinks make timing nondeterministic.
- Backpressure and sink failure need fault-injection tests.
- Retention and query permissions are outside normal unit tests.
- Cross-service correlation requires integration tests that cross queue and job
  boundaries.

Techniques that apply.

- **Event contract tests.** Validate required fields, enum values, schema
  version, timestamp format, actor form, target form, and outcome.
- **Golden query tests.** Store a small fixture set and verify the reviewer
  queries return expected records for actor, action, target, tenant, and time
  range.
- **Denied-path tests.** For every high-risk authorization rule, test both allow
  and deny paths. The denied path should produce a record where policy says it
  should.
- **Redaction tests.** Send inputs containing keys named password, token,
  secret, authorization, cookie, and private key. Assert they are absent or
  masked in the event.
- **Sink failure tests.** Simulate timeout, write failure, queue full, and
  process restart. Verify the configured choice: fail-closed, durable spool, or
  incident flag.
- **Idempotency tests.** Retry the same command and check whether the audit
  semantics match the domain semantics. A retry may produce one event with a
  retry count or two events tied by the same idempotency key.
- **Ordering tests.** For workflows with request and asynchronous completion
  events, assert correlation id and causal fields rather than relying only on
  wall-clock ordering.
- **Access tests.** Verify that app writers cannot read protected audit fields,
  reviewers cannot mutate records, and tenant reviewers cannot query outside
  their scope.

Verification should include volume. A service that emits correct records under
unit test can still fail under production volume because buffers fill or
collectors drop records.

## 16. Observability signals

Audit logging is itself a production subsystem. It needs its own telemetry.

What to record about the audit path.

- Counter of audit events emitted by service, action, outcome, tenant class, and
  detail level.
- Counter of events accepted by the sink, with the same labels.
- Difference between emitted and accepted counts over a window.
- Histogram of append latency by sink and event class.
- Gauge of local spool depth and oldest spooled event age.
- Counter of dropped events, redaction hits, schema validation failures, and
  sink errors.
- Counter of policy changes that alter which event classes are recorded.
- Storage growth, index growth, query latency, and retention deletion counts.
- Reviewer access events, including exports and broad searches.

A healthy instance on a dashboard. Emitted and accepted counters match after a
short delay. Append latency is small compared with the protected operation.
Spool depth returns to zero after bursts. Redaction hits are rare and explainable.
Schema validation failures are zero. Event mix changes line up with releases,
feature flags, or known traffic shifts. High-risk event classes have long
retention and active query views.

A failing instance. Emitted counts rise while accepted counts stall. The oldest
spooled event age grows. One service has many schema failures after a deploy.
Append latency has a long tail and user latency moves with it. A sudden drop in
privileged events follows a logging-policy change rather than a business
change. Export events spike outside review windows. Storage grows faster than
retention removes records. Tenant queries return cross-tenant results.

Use the audit log to watch itself. Record changes to audit policy, sink
configuration, retention settings, field access rules, export settings, and
reviewer role membership. Those events are among the most sensitive records in
the system because they affect the trustworthiness of later records.

## 17. Security and privacy implications

Engineering judgement: Audit Log closes one security gap and opens another.
It improves accountability, but it creates a new high-value data set.

Security gains.

- It creates evidence for policy violations, compromised accounts, suspicious
  automation, privilege escalation, and data export.
- It makes complete mediation easier to review because each protected decision
  can have a corresponding event.
- It supports incident response by joining actor, action, target, result,
  request id, and source.
- It can detect tampering when audit policy changes, sink failures, retention
  edits, and broad exports are themselves audited.

Security risks.

- Logs can be attacked for confidentiality, integrity, availability, and
  accountability. OWASP explicitly organizes attacks on logs under those four
  headings
  ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
  verified 2026-08-02).
- Audit records can contain secrets, personal data, policy details, and target
  identifiers. Field allowlists are safer than free-form payload capture.
- An attacker who gains write access to the audit path can flood it, hide
  signal with noise, or create false records.
- An attacker who gains delete or rewrite access can remove evidence unless the
  storage layer or export path resists tampering.
- Source IP and user agent are useful context but weak identity. Treat them as
  supporting facts, not proof of actor.
- Reviewer access can become a data-exfiltration path. Export events and broad
  searches need their own records and alerts.

Privacy implications.

- Minimize event detail to what review needs. Google Cloud's split between
  Admin Activity and Data Access logs is a useful example of separate classes
  with different volume and access profiles
  ([Google Cloud, "Cloud Audit Logs overview"](https://docs.cloud.google.com/logging/docs/audit?hl=en),
  verified 2026-08-02).
- Separate retention by event class. A role change may need longer retention
  than a low-risk read.
- Protect tenant boundaries in query tools. A central audit store does not mean
  every reviewer can see every tenant.
- Support legal hold and deletion policy without corrupting remaining history.
  This often means tombstones, redaction records, or separated detail payloads
  rather than editing core event facts in place.
- Do not record secrets, session tokens, raw authorization headers, private
  keys, full payment data, or request bodies unless a documented policy and
  access model allows it. OWASP's data exclusion guidance is the source for this
  caution
  ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
  verified 2026-08-02).

Where the pattern is silent. Audit Log does not authenticate users, authorize
requests, encrypt data, or prove non-repudiation by itself. OWASP cautions that
non-repudiation is hard to achieve for logs because trust often depends on the
audited logging party, while digital signatures are hard to use in practice
([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html),
verified 2026-08-02). Treat the audit log as evidence whose strength depends on
identity, clock, storage, access control, and operational process.
