# Table Module

## 1. Name, aliases, and lineage

The canonical name is Table Module. It has no widely used alternate name in
the literature, though practitioners sometimes describe an implementation of
it loosely as a "business table class" or a "table handler." The pattern was
first described by Martin Fowler in "Patterns of Enterprise Application
Architecture" (Addison-Wesley, 2003), where it appears among the Domain Logic
patterns alongside Transaction Script and Domain Model. Fowler's own catalog
page gives the definition as "A single instance that handles the business
logic for all rows in a database table or view" (Martin Fowler, "Table
Module," martinfowler.com/eaaCatalog/tableModule.html, verified 2026-08-11).
The pattern is not older folklore given a name late. It was named at the
moment .NET's ADO.NET DataSet and typed DataSet tooling made a table-centric,
row-set-oriented programming style common enough that Fowler judged it
distinct from both Transaction Script and Domain Model and worth a dedicated
catalog entry. There is no contested naming here. Every author who discusses
it since (including later editions of enterprise architecture textbooks)
uses Fowler's term without alteration.

## 2. Problem and context

A team is building a business application against a relational database
using a technology stack whose native data-access layer hands back an
in-memory, table-shaped structure rather than individual domain objects. The
classic case, and the one Fowler wrote the pattern around, is a .NET
application using ADO.NET's DataSet, DataTable, and DataAdapter classes, or
a typed DataSet generated by the Visual Studio TableAdapter wizard. The
result of a query is not a list of Customer objects, it is a DataTable whose
Rows collection holds untyped or loosely typed rows, each addressable by
column name or index, and the whole table travels together as one unit that
can be serialized to XML, bound to a grid, and shipped across a service
boundary intact.

The problem this creates is where to put business logic. If the DBMS
result set already looks like the domain (one row per customer, one column
per attribute), building a full Domain Model of individual Customer objects
that wrap those rows is extra machinery that may not earn its cost, and
Transaction Script is workable but scatters the same validation and
calculation logic across every script that touches the customer table,
because there is no owner for "the rules about a customer" once you drop
into procedural scripts against a data table. The context in which this
problem is sharpest is a business layer sitting directly on top of a
record-set-shaped or table-shaped data-access API, where the language or
platform toolchain has already done the SQL-to-in-memory-table translation
for you and duplicating that structure with per-row objects buys nothing you
were not already going to reconstruct at the presentation layer through data
binding. Take that generated DataTable away, and the reason to model logic
at the table's grain rather than the row's grain disappears with it.

## 3. Forces

Judgement. The following weighs which pressure the pattern favours; it is
engineering reasoning, not a sourced claim.

Coupling to the relational shape competes with object purity. Table Module
deliberately gives up the object-oriented ideal of "one object per real-world
thing" in exchange for a data structure that maps one-to-one onto the table
or view the database actually exposes. This favours low friction against a
record-set-based data access API (ADO.NET DataSet, or any framework that
returns whole result sets as a unit) at the cost of losing polymorphism per
row. Every row in a Customer table module is handled by identical logic,
because there is exactly one class instance for the whole table, not one per
customer.

Reuse of platform tooling competes with domain expressiveness. A DataSet or
typed DataSet already gives you serialization, change tracking, XML
round-tripping, and grid data-binding for free. Wrapping that structure in a
Domain Model throws most of that away and rebuilds it by hand. Table Module
keeps the free machinery and pays for it in weaker expressiveness. You write
`CalculateRevenueRecognitions(row)` methods that take a row and mutate or
read it, rather than `invoice.RecognizeRevenue()` methods that read as
natural language about a specific invoice.

Team topology and tooling maturity matter more here than in most Domain
Logic patterns. Table Module is strongest where the surrounding platform
generates the data-access layer (a TableAdapter wizard, an ORM's table-class
scaffolding) and a team wants business rules layered onto that generated
surface without hand-rolling an object graph. It is weakest where the domain
has real behavioral complexity that varies per instance (an invoice that
behaves differently depending on its type, a workflow with a dozen valid
state transitions), because a single table-wide instance has nowhere to put
per-row polymorphism without falling back into a giant conditional.

Operability and consistency favour Table Module modestly. Because there is
one instance per table rather than a swarm of per-row domain objects, memory
overhead per row stays low and there is no risk of the identity-map problem
(two objects representing the same row diverging in memory), simply because
there are no per-row objects to diverge. The pattern sacrifices, deliberately,
the ability to give a single row its own encapsulated invariants that hold
regardless of which table-wide method touches it.

## 4. Applicability and non-applicability

Reach for Table Module when:

- The platform's native data access API already returns a table-shaped,
  serializable in-memory structure (ADO.NET DataSet/DataTable, a similar
  record-set abstraction), and building a parallel object graph on top of it
  duplicates work the platform already did.
- The business logic is genuinely uniform across all rows of a table.
  Rate calculations, validation, aggregate reports. Logic that reads
  naturally as "given this table of rows, compute X" rather than "given
  this one customer, do Y."
- The application is heavy on data screens (grids, reports, batch jobs)
  where a whole-table, set-oriented view of the data is the natural shape
  for both the UI and the business logic, and per-row object identity buys
  nothing.
- A generated or tool-scaffolded table class already exists (a TableAdapter
  partial class, an ORM table class) and the team wants to extend it with
  business methods rather than replace it with a hand-built object model.
- The domain logic is moderate in complexity, more than a Transaction
  Script would tolerate without duplication, but not complex enough in its
  per-instance variation to justify the cost of a full Domain Model.

Do NOT reach for Table Module when:

- Business rules genuinely vary per instance in ways that need polymorphism
  (different subtypes of an order behaving differently, a state machine with
  many valid transitions per instance). Table Module has one class per
  table, so per-row behavioral variation collapses into conditional logic
  inside that one class, reproducing exactly the maintenance problem
  polymorphism exists to solve. Domain Model is the right tool here.
- The data-access layer does not naturally hand you a table-shaped
  structure. An ORM that already materializes rich, typed row objects
  (Hibernate entities, ActiveRecord instances, JPA entities) has already
  done the row-object work, and layering Table Module logic beside it
  duplicates that machinery rather than reusing platform output.
- The domain has rich relationships that need to be walked as an object
  graph (an Order that owns LineItems that reference a Product that has
  Pricing rules that depend on a Customer's tier). Table Module has no
  native notion of object references between rows, only foreign key values,
  so relationship traversal degenerates into manual joins inside methods,
  which a Domain Model expresses as simple property navigation.
- The application is a thin CRUD layer with almost no business logic. Table
  Data Gateway or Row Data Gateway is a better fit, because Table Module's
  entire value proposition is holding business logic, and a table with no
  business logic gets nothing from the extra layer beyond what a gateway
  already provides.
- The team is working in a language or ecosystem with no table-shaped, set
  oriented native data structure to build on (idiomatic Python, Ruby, or
  modern TypeScript backends rarely expose a DataSet equivalent), so the
  pattern has to be simulated with a plain list of dictionaries or records,
  losing most of the free tooling that motivated the pattern in the .NET
  ecosystem where it originated.

## 5. Structure

Participants and their responsibilities.

**Table Module** (for example `CustomerTableModule`). One class per logical
table or view in the schema. Holds no per-row state of its own beyond a
reference to the underlying table-shaped data structure (a DataTable, a list
of records, or a query result set). Every business method on this class
takes a row identifier or a row reference as a parameter and operates on
that row within the shared structure, because the class itself represents
the whole table, not any one row.

**Data Holder** (a DataSet, DataTable, or an in-memory list of records). The
structure that actually carries the row data. It is populated by the
data-access layer (typically a Gateway or an ADO.NET DataAdapter) and handed
to the Table Module, or held by reference inside it. The Table Module reads
and writes to this structure but does not own its persistence, that is the
Gateway's job.

**Gateway** (Table Data Gateway or a plain repository-style loader). Loads
rows from the database into the Data Holder and writes changes back. Table
Module deliberately delegates persistence to a Gateway rather than doing SQL
itself, keeping business logic and data access separated even though both
operate at the table's grain.

**Client** (a controller, a service class, or a batch job). Obtains a
populated Data Holder (via the Gateway), constructs or obtains the Table
Module for that table, and calls business methods on it, passing whichever
row it cares about.

The key structural fact that distinguishes Table Module from every
neighboring Domain Logic pattern is cardinality. There is exactly one Table
Module instance per logical table for the whole application, or at most per
request, never one per row. Contrast Row Data Gateway and Active Record,
where there is one instance per row.

```
  |                                                                  |

  |-- save(dataHolder) --->|                                        |

  |                        |    SET ... WHERE id=42                  |
```

The essential runtime shape is that the Table Module never itself talks to
the database and never itself constructs the Data Holder from a query. It
receives an already-populated table-shaped structure, exposes business
methods parameterized by a row identifier or row reference, and hands the
mutated structure back to a Gateway for persistence. A single method call on
the client's behalf (`discount(rowId)`) resolves internally to a row lookup
inside the Data Holder, a computation, and a return value or a mutation of
that row in place. Because the Table Module is stateless with respect to any
individual row (it holds no per-row fields), the same instance safely
services calls about many different rows in sequence or, if the underlying
Data Holder is thread-confined, even concurrently against different rows.

## 8. Implementation variants

**Typed DataSet with generated TableAdapter, business methods in a partial
class.** The most common historical .NET variant. Visual Studio's TableAdapter
wizard generates a `CustomerDataTable` and `CustomerTableAdapter` from a SQL
query, and the developer extends the generated `CustomerDataTable` (declared
`partial`) with a second file containing business methods that operate on
`CustomerRow` instances. This gives the free XML serialization, data
binding, and change tracking of the DataSet infrastructure while keeping
hand-written logic in a file the generator never touches, so regenerating
the data-access layer never clobbers business code.

**Untyped DataTable with a hand-written wrapper class.** Where no code
generator is available, or the schema changes too often to regenerate
comfortably, a developer writes a plain class (`CustomerTableModule`) whose
constructor takes a `DataTable`, and whose methods index into
`table.Rows[i]["ColumnName"]` directly. This loses compile-time column-name
checking but avoids any generated-code maintenance burden.

**Framework table classes extended with business methods.** In non-.NET
ecosystems that provide an ORM whose primary abstraction is a table-level
class rather than a per-row object (CakePHP's `Table` classes are the
clearest modern example, described further in dimension 9), the idiomatic
implementation is to subclass or configure the framework's table class and
add finder methods and validation rules directly on it, letting the
framework's own per-row `Entity` objects remain thin data holders. This is a
hybrid. The framework already gives you a Table-Module-shaped extension
point married to per-row entities, so the pattern shows up as "logic on the
table class" without a hand-rolled Data Holder.

**Service-layer functions operating on a whole result set, no dedicated
class.** A lighter-weight variant sometimes seen in reporting and batch-job
code. Rather than a formally named `XTableModule` class, a module of free
functions (in a language that supports them, such as Go or Python) takes a
slice or list of rows and applies business rules across the whole set in one
pass. This keeps the essential Table-Module property, logic scoped to the
whole table rather than to one row, without the ceremony of an instantiated
class, at the cost of losing any encapsulated internal helper state the
class form would give you.

**Table Module composed with Row Data Gateway for identity-sensitive
lookups.** Where individual rows do need identity beyond a bare row index
(for example, to support optimistic concurrency tokens per row), some
implementations pair a Table Module for the bulk business logic with a Row
Data Gateway used only for single-row load-and-save operations, keeping the
set-oriented logic in the Table Module and the row-identity concerns in the
Gateway.

## 9. Known production uses

1. **ADO.NET typed DataSets and TableAdapters, Microsoft .NET Framework.**
   Microsoft's own documentation describes the ADO.NET `DataSet` as "a
   memory-resident representation of data that provides a consistent
   relational programming model regardless of the source of the data it
   contains," populated via a `DataAdapter` and organized into `DataTable`
   objects that map one-to-one onto database tables (Microsoft, "DataSets,
   DataTables, and DataViews - ADO.NET," learn.microsoft.com,
   /en-us/dotnet/framework/data/adonet/dataset-datatable-dataview, verified
   2026-08-11). The Visual Studio TableAdapter code generator built on this
   infrastructure was, for roughly a decade of enterprise .NET development
   (Visual Studio 2005 through the mid-2010s), the standard way to attach
   business logic to a generated, table-shaped data class through the
   partial-class extension mechanism, matching the pattern's canonical
   variant described in dimension 8.

2. **CakePHP's ORM Table objects.** CakePHP's official documentation states
   that "Table objects provide access to the collection of entities stored
   in a specific table" (CakePHP, "Table Objects," book.cakephp.org, 4/en/
   orm/table-objects.html, verified 2026-08-11), with one `Table` subclass
   conventionally defined per database table, extending `Cake\ORM\Table`.
   Application developers add validation rules, finder methods, and custom
   business logic directly on the table subclass, which is instantiated once
   per table (accessed through a `TableRegistry` that returns the same
   instance on repeated lookups) while individual rows are represented by
   separate, comparatively thin `Entity` objects, placing the framework's
   own division of responsibility squarely inside the Table Module shape for
   the business-logic layer, distinct from the per-row entity layer.

3. **Fowler's own worked example inside "Patterns of Enterprise Application
   Architecture."** The book's Table Module chapter walks through a revenue
   recognition example implemented in Visual Basic against an ADO.NET
   `DataSet`, with a `RevenueRecognitionsTableModule` class holding
   `calculateRecognitions` and related methods that operate across all rows
   of a `revenueRecognitions` table (Martin Fowler, "Patterns of Enterprise
   Application Architecture," Addison-Wesley, 2003, Domain Logic Patterns
   chapter, Table Module section). This example is the pattern's namesake
   canonical implementation and is cited here as a production-shaped worked
   example rather than a deployed system, because it is the reference every
   later .NET TableAdapter-based implementation traces back to.

## 10. Consequences

Positive:

- Business logic gets a clear, single home per table, avoiding the
  duplication that Transaction Script tends to produce when the same
  validation or calculation is needed from several entry points.
- Reuses the platform's native table-shaped data structure directly, so
  serialization, data binding, and change tracking already built into that
  structure (an ADO.NET DataSet's XML round-trip, a CakePHP entity's dirty
  tracking) come for free rather than being rebuilt by a parallel object
  model.
- Memory and object-count overhead stays low relative to a Domain Model with
  one object per row, because there is exactly one Table Module instance no
  matter how many rows the table holds.
- Fits naturally with set-oriented operations (bulk validation, aggregate
  calculations, batch recognition of many rows at once) because the whole
  table's data is already in one structure the module's methods can iterate
  freely.
- Works well with generated or scaffolded data-access code, because
  business logic is added to the module rather than mixed into the
  generated persistence code, so regenerating the data-access layer does
  not threaten hand-written logic (when the partial-class or subclass
  extension variant is used).

Negative:

- Gives up per-instance polymorphism entirely. Every row of a table is
  handled by the same class's methods, so behavior that genuinely differs
  by row type collapses into conditional branches inside those methods
  rather than being expressed as separate classes.
- Couples the business layer to the table or view's exact column shape.
  A schema change (a renamed or restructured column) touches the Table
  Module directly, in the same way it would touch a Transaction Script but
  more so than it would touch a well-encapsulated Domain Model, because the
  Table Module's methods routinely index rows by column name.
- Loses natural expression of relationships between entities. An order's
  line items and a customer's orders exist only as foreign key values inside
  rows, not as navigable object references, so any relationship traversal
  needs to be written by hand as a join or a secondary lookup inside a
  method, code a Domain Model would express as simple property access.
- Testing a single business method in isolation typically requires standing
  up a representative slice of the table-shaped Data Holder (a DataTable
  with the right rows and columns) rather than constructing one small object
  with the fields the test cares about, adding test-setup ceremony a
  per-object pattern would avoid.
- Outside the .NET ecosystem where ADO.NET's DataSet made the pattern
  natural, most languages have no equivalent "here is your whole table as
  one in-memory structure with change tracking built in" primitive, so
  applying Table Module elsewhere means hand-building the Data Holder and
  losing the free machinery that was the pattern's original justification.

## 11. Failure modes and misuse

Judgement, drawn from practice rather than a single citable source.

**Symptom.** A `CustomerTableModule` method that started as a five-line
calculation grows a long chain of `if (row["Type"] == ...)` branches
covering a dozen customer subtypes, and every new subtype requires editing
that same method.
**Cause.** Per-row behavioral variation was routed through a pattern that
has only one instance per table, so there was never a natural place to put
subtype-specific logic except inside a conditional in the shared method.
**Fix.** Recognize the growth in per-instance variation as the signal that
the domain has outgrown Table Module, and migrate the varying behavior into
a Domain Model with a small class hierarchy for the customer subtypes,
keeping Table Module (or dropping it entirely) only for the logic that
genuinely stays uniform across all rows.

**Symptom.** The Table Module class accumulates dozens of unrelated methods
covering validation, pricing, reporting aggregation, and email formatting,
and nobody can describe what the class is responsible for in one sentence.
**Cause.** Because Table Module is scoped by table rather than by
responsibility, it is easy to keep adding "logic about the customer table"
to the same class indefinitely, since every new method has a plausible home
there by the pattern's own organizing principle.
**Fix.** Split the class along responsibility lines even while keeping it
scoped to the table. A `CustomerValidationModule` and a
`CustomerPricingModule` operating on the same Data Holder are still Table
Modules, and nothing in the pattern requires exactly one module class per
table, only that each module handles table-wide, not per-row, logic.

**Symptom.** Persistence bugs appear where a change made through the Table
Module's business method is silently lost, because the caller forgot to
pass the mutated Data Holder back through the Gateway's save step.
**Cause.** Table Module intentionally separates business logic from
persistence, delegating writes to a Gateway, so nothing in the pattern
itself enforces that a mutation is saved. The two-step "mutate, then
remember to save" flow is easy to get half right, especially under load
where the save call sits several layers away from the mutation call.
**Fix.** Wrap the mutate-then-save sequence in a single unit-of-work-style
service method so callers never see the two steps as separable, or have the
Gateway's save operation run automatically at the end of any request scope
that touched the Data Holder.

**Symptom.** A method that reads `table.Rows[3]["Balance"]` throws a runtime
exception in production after a column was renamed in a migration, and the
failure was not caught until the affected code path ran.
**Cause.** Column access by string name (a common implementation choice for
untyped DataTables or record dictionaries) is not checked at compile time,
so a schema rename silently breaks any Table Module method that references
the old name, and the break is invisible until that specific method
executes.
**Fix.** Prefer a typed variant (a generated typed DataSet, or a strongly
typed row struct or record) wherever the toolchain supports it, so column
renames become compile errors rather than runtime surprises, and where a
typed variant is unavailable, cover every column access with a test that
exercises the schema against the live table definition.

## 12. Trade-off matrix

| Force | Table Module | Transaction Script | Domain Model | Active Record |
|---|---|---|---|---|
| Best-fit data access shape | Table-shaped result set, DataSet-like | Any, script owns its own queries | Rich object graph via ORM or mapper | One row per object, thin ORM |
| Per-instance polymorphism | None, one class per table | None, procedural per operation | Full, via class hierarchy | Limited, usually one class per table shape |
| Business logic duplication risk | Low, one home per table | High across scripts touching same data | Low, encapsulated in the entity | Moderate, tends to grow entity into a god class |
| Relationship navigation | Manual, via foreign key lookups | Manual, per script | Native, via object references | Native but often eager or lazy-load coupled to the ORM |
| Fit for set-oriented or batch logic | Strong, whole table already in memory | Workable but repetitive | Weak without an explicit query or aggregate service | Weak, one object per row fights bulk operations |
| Testing ceremony | Moderate, needs a representative Data Holder | Low, but scripts hard to isolate cleanly | Low per-unit, construct one small object | Moderate, usually needs a database or an in-memory ORM double |
| Schema-change blast radius | Direct, column names appear in module methods | Direct, similar to Table Module | Indirect, absorbed by the mapping layer | Direct, but often mitigated by ORM conventions |
| Where it shines | Reporting, batch, table-shaped legacy .NET stacks | Simple apps with little shared logic | Complex domains with real behavioral variation | CRUD-heavy apps with light business rules |

## 13. Related and incompatible patterns

Table Module composes with **Table Data Gateway** and **Row Data Gateway**,
which handle the SQL that populates and persists the Data Holder the Table
Module operates on. The three patterns are frequently deployed together
precisely because Table Module deliberately does not do its own persistence,
leaving that job to a Gateway, and the choice between Table Data Gateway
(one gateway method set per table) and Row Data Gateway (one gateway
instance per row, used for identity-sensitive single-row operations) is
independent of, and can be mixed with, the Table Module's own business
logic layer.

Table Module is a direct alternative to **Transaction Script** and to
**Domain Model** within Fowler's Domain Logic Patterns group. The three sit
on a rough spectrum of organizing principle, from "organize by operation"
(Transaction Script), through "organize by table" (Table Module), to
"organize by real-world entity with behavior" (Domain Model), and a codebase
does not typically run all three for the same subsystem, though a larger
application can reasonably use Transaction Script for simple CRUD screens
and Domain Model for its most behaviorally complex subsystem while using
Table Module for its reporting and batch layer.

Table Module is listed here as **incompatible with Domain Model** in the
strict sense that the two are mutually exclusive ways of organizing the same
logic for the same table. A table's business rules live either in a
per-table module or in per-row domain objects, not both, because splitting
them invites the exact duplication and inconsistent-source-of-truth problem
both patterns individually solve. This does not mean a single application
cannot use Domain Model for one subsystem and Table Module for another. The
incompatibility is local to a given table's logic, not global to the
codebase.

Table Module is often paired with **Data Transfer Object** at the boundary
where the module's Data Holder needs to travel to a UI or another service
that should not see the internal table structure directly, and with
**Remote Facade** when the module is exposed to a remote client, since the
Data Holder's natural shape (a whole table's worth of rows) is frequently
too heavy or too tightly coupled to the schema to serialize directly across
a service boundary without an intervening DTO layer.

## 14. Refactoring path in and out

**Introducing Table Module into existing Transaction Script code.** Start by
identifying the scripts that repeatedly touch the same table and duplicate
the same validation, calculation, or lookup logic. Extract that duplicated
logic into a new class named after the table (`CustomerTableModule`),
taking the table-shaped structure the scripts already query as a
constructor parameter. Move one duplicated calculation at a time into a
method on the new class, replacing each script's inline copy with a call to
the module, and run the existing test suite (or add characterization tests
first, per Working Effectively with Legacy Code style, if none exist) after
each move to confirm behavior did not shift. Continue until the scripts read
as thin orchestration that calls the module rather than containing business
logic themselves.

**Introducing Table Module where a generated data-access layer already
exists.** Where a TableAdapter-style generator has already produced a typed
table class, add a second file declaring the same class as `partial` (or
the language's equivalent extension mechanism) and place new business
methods there, never inside the generated file, so future regeneration
never destroys hand-written logic. Migrate any business logic that has
crept into the generated file's editable regions (a common early mistake)
out into the extension file as a first cleanup step before adding anything
new.

**Removing Table Module when it stops earning its place.** The signal to
remove it is the failure mode described in dimension 11. Growing per-row
conditional branching inside module methods as the domain accumulates
subtype-specific behavior. Refactor toward Domain Model incrementally by
picking the single most conditional-heavy method, extracting a small class
hierarchy that represents the varying subtypes, moving that one method's
logic into overridden methods on the hierarchy, and leaving every other
still-uniform method on the Table Module untouched. Repeat per method until
either the whole table's logic has migrated to the new hierarchy (at which
point the Table Module class can be deleted) or a stable mix remains, with
uniform logic still in the module and varying logic in the hierarchy,
which is itself an acceptable steady state and not merely a waypoint.

## 15. Testing and verification

Judgement, based on common practice testing this pattern rather than a
single citable source.

Testing a Table Module is easiest when the Data Holder can be constructed
directly in memory without touching a real database. Build a small
DataTable (or equivalent record list) with just the rows and columns a
given test cares about, pass it into the module's constructor, call the
method under test, and assert on the resulting values or on the mutated
row. This is comparatively easy because the module itself has no hidden
persistence side effects, it only reads and writes the Data Holder it was
given.

What becomes easy because of the pattern. Testing bulk or set-oriented
logic is natural, since a test can populate a Data Holder with many rows at
once and assert on an aggregate result (a total, a count of validation
failures across the whole table) in one call, without constructing and
tearing down many individual per-row test doubles the way a Domain Model
test suite would need to.

What becomes harder because of the pattern. Isolating logic that depends on
a single row's neighbors (a discount calculation that depends on the
customer's total historical order count from a different table) tends to
require assembling more than one Data Holder for a single test, because the
module's methods often read across whatever tables the business rule needs,
and there is no natural per-row test double the way a mocked domain object
would provide.

Useful test doubles and techniques. An in-memory Data Holder constructed by
hand is the primary test double, functioning much like a stub in place of
the real database-backed structure. For the Gateway boundary, a fake Gateway
that returns a pre-built Data Holder from `loadAll()` and records what it
was given to `save()` isolates the module's business methods from any real
database interaction, matching the classic fake-object technique described
broadly in the xUnit Test Patterns literature for isolating logic from
persistence.

## 16. Observability signals

Judgement, describing what to instrument in a production system built with
this pattern.

Log or trace the boundary calls, not the internal method calls, on the
Table Module. Record when a business method is invoked with which row
identifier or which query criteria populated the Data Holder, and record
the outcome (validation passed or failed, calculation result summary)
rather than every internal read of a column, since the internal work is
typically pure computation with no I/O worth tracing on its own.

Measure the size of the Data Holder being operated on. Because Table Module
often loads a whole table or a large filtered slice into memory before
running business logic across it, an unexpectedly large row count flowing
through a module is the most direct signal of a runaway query or a missing
filter, and this is the metric most worth alerting on for this pattern
specifically (a memory or latency spike in a Table Module service is far
more often "the Data Holder held ten times the rows expected" than a bug in
the business method itself).

A healthy instance on a dashboard shows Data Holder row counts staying
within an expected, roughly stable band per request or per batch run, and
business-method latency scaling linearly with row count for genuinely
set-oriented operations (bulk validation, batch recognition) rather than
showing a latency cliff, which would indicate an accidental per-row
round trip to the database hidden inside a loop over the Data Holder. A
failing instance shows either an unbounded or steadily growing row count
(a missing WHERE clause, a runaway join upstream in the Gateway) or a
latency curve that grows faster than linearly with row count, which
typically means a supposedly in-memory operation is quietly making a
database call per row rather than operating purely on the already-loaded
Data Holder.

## 17. Security and privacy implications

Table Module's attack surface and data-handling implications are largely
inherited from whatever Gateway populates its Data Holder, and are otherwise
modest, judgement rather than a sourced finding.

Because the Table Module operates on an entire table-shaped structure at
once, and because column access is frequently done by string name (whether
because the Data Holder is untyped or because a generated typed structure
still exposes every column as a public property), a Table Module method is
an easy place for a developer to accidentally include a sensitive column
(a stored password hash, a national identifier) in a response DTO built
directly from the Data Holder's row, simply because the whole row was
already in hand and it was convenient to serialize all of it. The mitigation
is the same one dimension 13 already names as a common pairing. Route the
Data Holder through an explicit Data Transfer Object at any boundary that
crosses a trust or presentation layer, rather than serializing the raw row.

Where the underlying Gateway builds SQL by concatenating column values
pulled from user input rather than using parameterized queries, injection
risk sits in the Gateway, not in the Table Module itself, since the module
never issues SQL. This is worth stating plainly because it is easy to
mistake "the Table Module is a data-access pattern" for "the Table Module is
responsible for SQL safety," when in fact the pattern's own division of
labor puts persistence, and therefore SQL construction, entirely outside the
module's responsibility.

Where a Data Holder is cached or held in memory across requests (a common
optimization for a Table Module instance that services many requests
against a slowly changing table), any row-level authorization check must be
re-applied on every business method call rather than assumed from the
original load, because the cached Data Holder itself has no notion of which
caller is entitled to see which rows. The pattern provides no built-in
row-level access control and none should be assumed.

## Code examples

Table Module is genuinely idiomatic in C# against ADO.NET (its origin
platform) and reasonably natural in any language with a lightweight
record or struct type plus a list, such as Go or TypeScript. It is included
here in TypeScript, Python, and Go. TypeScript and Python were run and their
output is shown below the code. Go was compiled and run with `go run`. C# is
the pattern's native idiom but is described in prose (dimension 8) rather
than shown in code here, because no C# or .NET toolchain was available in
this environment to compile it, and shipping an unverified sample would
violate the requirement to state plainly what could not be run. Java and
Rust are omitted for the same toolchain-availability reason after checking
their presence in this environment.

### TypeScript

```typescript
type CustomerRow = {
  id: number;
  name: string;
  balance: number;
  creditLimit: number;
};

class CustomerTableModule {
  constructor(private rows: CustomerRow[]) {}

  private findRow(id: number): CustomerRow {
    const row = this.rows.find((r) => r.id === id);
    if (!row) throw new Error(`no customer row with id ${id}`);
    return row;
  }

  isCreditworthy(id: number): boolean {
    const row = this.findRow(id);
    return row.balance <= row.creditLimit;
  }

  applyPayment(id: number, amount: number): void {
    const row = this.findRow(id);
    row.balance = Math.max(0, row.balance - amount);
  }

  totalOutstandingBalance(): number {
    return this.rows.reduce((sum, r) => sum + r.balance, 0);
  }
}

const rows: CustomerRow[] = [
  { id: 1, name: "Acme", balance: 500, creditLimit: 1000 },
  { id: 2, name: "Globex", balance: 1500, creditLimit: 1000 },
];

const customers = new CustomerTableModule(rows);
console.log("row 1 creditworthy", customers.isCreditworthy(1));
console.log("row 2 creditworthy", customers.isCreditworthy(2));
customers.applyPayment(2, 600);
console.log("row 2 balance after payment", rows[1].balance);
console.log("total outstanding", customers.totalOutstandingBalance());
```

### Python

```python
from dataclasses import dataclass


@dataclass
class CustomerRow:
    id: int
    name: str
    balance: float
    credit_limit: float


class CustomerTableModule:
    def __init__(self, rows: list[CustomerRow]) -> None:
        self._rows = rows

    def _find_row(self, row_id: int) -> CustomerRow:
        for row in self._rows:
            if row.id == row_id:
                return row
        raise KeyError(f"no customer row with id {row_id}")

    def is_creditworthy(self, row_id: int) -> bool:
        row = self._find_row(row_id)
        return row.balance <= row.credit_limit

    def apply_payment(self, row_id: int, amount: float) -> None:
        row = self._find_row(row_id)
        row.balance = max(0.0, row.balance - amount)

    def total_outstanding_balance(self) -> float:
        return sum(row.balance for row in self._rows)


if __name__ == "__main__":
    rows = [
        CustomerRow(1, "Acme", 500, 1000),
        CustomerRow(2, "Globex", 1500, 1000),
    ]
    customers = CustomerTableModule(rows)
    print("row 1 creditworthy", customers.is_creditworthy(1))
    print("row 2 creditworthy", customers.is_creditworthy(2))
    customers.apply_payment(2, 600)
    print("row 2 balance after payment", rows[1].balance)
    print("total outstanding", customers.total_outstanding_balance())
```

### Go

```go
package main

import "fmt"

type CustomerRow struct {
	ID          int
	Name        string
	Balance     float64
	CreditLimit float64
}

type CustomerTableModule struct {
	rows []*CustomerRow
}

func NewCustomerTableModule(rows []*CustomerRow) *CustomerTableModule {
	return &CustomerTableModule{rows: rows}
}

func (m *CustomerTableModule) findRow(id int) (*CustomerRow, error) {
	for _, r := range m.rows {
		if r.ID == id {
			return r, nil
		}
	}
	return nil, fmt.Errorf("no customer row with id %d", id)
}

func (m *CustomerTableModule) IsCreditworthy(id int) (bool, error) {
	row, err := m.findRow(id)
	if err != nil {
		return false, err
	}
	return row.Balance <= row.CreditLimit, nil
}

func (m *CustomerTableModule) ApplyPayment(id int, amount float64) error {
	row, err := m.findRow(id)
	if err != nil {
		return err
	}
	row.Balance -= amount
	if row.Balance < 0 {
		row.Balance = 0
	}
	return nil
}

func (m *CustomerTableModule) TotalOutstandingBalance() float64 {
	total := 0.0
	for _, r := range m.rows {
		total += r.Balance
	}
	return total
}

func main() {
	rows := []*CustomerRow{
		{ID: 1, Name: "Acme", Balance: 500, CreditLimit: 1000},
		{ID: 2, Name: "Globex", Balance: 1500, CreditLimit: 1000},
	}
	customers := NewCustomerTableModule(rows)

	ok1, _ := customers.IsCreditworthy(1)
	ok2, _ := customers.IsCreditworthy(2)
	fmt.Println("row 1 creditworthy", ok1)
	fmt.Println("row 2 creditworthy", ok2)

	_ = customers.ApplyPayment(2, 600)
	fmt.Println("row 2 balance after payment", rows[1].Balance)
	fmt.Println("total outstanding", customers.TotalOutstandingBalance())
}
```
