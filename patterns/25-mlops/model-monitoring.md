# Model Monitoring

## 1. Name, aliases, and lineage

Model monitoring is the ongoing, in-production practice of observing a
deployed model's data quality, prediction behavior, operational health,
and eventual measured accuracy after it has already been shipped, as
distinct from any check performed before or at the moment of deployment.
There is no single canonical originator for this practice, it is an
emergent industry discipline that converged from three independent
directions across roughly 2015 to 2020, each independently verifiable.

Sculley and colleagues, in Hidden Technical Debt in Machine Learning
Systems, supplied the theoretical justification the field still uses for
why this is a structural necessity rather than a nice-to-have, using the
software engineering framework of technical debt, we find it is common to
incur massive ongoing maintenance costs in real-world machine learning
systems, naming boundary erosion, entanglement, hidden feedback loops,
undeclared consumers, data dependencies, configuration issues, and changes
in the external world as the specific ML risk factors that make this so.

Google's own Rules of Machine Learning gives several rules directly about
post-deployment observation, distinct from the narrower, single-point-in-time
training-serving skew rules covered elsewhere in this family. Rule 8, know
the freshness requirements of your system, asks how much performance
degrades if a model is a day old, a week old. Rule 10, watch for silent
failures, gives the exact articulation of the no-exception-thrown problem
that motivates this whole practice, a stale, no-longer-updated joined
table can decay gradually, sometimes you find tables that are months out
of date. Rule 24, measure the delta between models, describes running both
a candidate and the live model and looking at the size of the symmetric
difference, a monitoring technique this family's champion-challenger entry
also touches from the deployment side.

Uber's Michelangelo platform documented a production monitoring layer as a
first-class platform component years before commercial monitoring tooling
existed, automatically logging and optionally holding back a percentage of
served predictions, later matched with observed outcomes generated by the
data pipeline, and for regression models publishing R-squared, root mean
square logarithmic error, root mean square error, and mean absolute error
to Uber's own time series monitoring system with threshold alerts.

## 2. Problem and context

A deployed model does not throw an exception when it gets worse. AWS's
own model quality monitoring documentation states the core mechanism this
practice exists to solve, model quality monitoring jobs monitor the
performance of a model by comparing the predictions that the model makes
with the actual ground truth labels that the model attempts to predict,
and its current replacement-stack guidance names the reason that
comparison is fundamentally delayed, including a pattern for reconciling
delayed ground truth with predictions by inference identifier, which
addresses the real world label latency that makes model quality monitoring
difficult.

AWS separately frames the concrete business context this problem sits in,
predictive models can silently degrade in production, fraud handlers start
seeing false positive spikes, loan officers see applications that should
have been flagged, and planners end up with excess inventory from
overestimated demand. This context, a high-stakes, high-volume,
feedback-loop-bearing model whose real-world environment keeps moving
while the model's own parameters stay frozen at training time, is exactly
where this practice earns its cost.

## 3. Forces

Cost and compute overhead sit against detection speed. AWS's current
replacement-stack guidance names its own cost-conscious architecture
directly, compute scales to zero when idle, an event-driven scheduled job
runs drift analysis rather than an always-on service, and a partitioned
data-lake table keeps scan costs low as data volume grows. The same
guidance documents AWS's own resolution of this tension in the other
direction, its managed SageMaker Model Monitor service is no longer open
to new customers, existing customers can continue to use the service as
normal, AWS continues to invest in security and availability improvements
for Model Monitor, but does not plan to introduce new features, with AWS
now recommending the self-managed, cost-controlled open-source stack
instead.

Delayed ground truth sits against immediacy. The eventId and inferenceId
join mechanism covered in section 5 exists specifically because a
prediction's correctness is often unknowable until days or weeks after the
prediction was made, a loan default, a customer's eventual churn. Fiddler's
own product documentation confirms the field treats this as a first-class
design concern rather than an edge case, its platform explicitly lets a
person update ground truth labels in a delayed, asynchronous fashion.

Structural, ML-specific risk sits against the illusion that monitoring
operational health alone is sufficient. Sculley and colleagues name
entanglement and hidden feedback loops as risks a purely operational
dashboard, latency, error rate, throughput, cannot surface, because a
model can be fast, available, and quietly wrong at the same time. This
entry could not find a source stating alert fatigue as an explicitly
named, ML-monitoring-specific tension, distinct from the general software
alerting discipline it inherits, and states that plainly rather than
inventing an ML-specific citation for it.

## 4. Applicability and non-applicability

Reach for dedicated model monitoring on any model whose real-world
environment moves while the model itself stays fixed, and where a wrong
prediction carries real cost. AWS's own applicability framing names this
category directly, fraud handlers seeing false positive spikes, loan
officers seeing applications that should have been flagged, planners
overestimating demand, high-stakes, high-volume, feedback-loop-bearing
models. The practice is not limited to always-on, real-time serving, AWS
ships a batch monitoring pipeline solution alongside its real-time
solution, so a model scored on a recurring schedule is squarely within
scope too.

Non-applicability is less directly sourced and this entry states that
honestly. This entry found one concrete, tool-specific size boundary,
Databricks' snapshot profile type has a hard maximum table size of four
terabytes, per its own documentation, a real ceiling for that one
implementation rather than a general rule. Beyond that, no fetched source
stated an explicit exclusion such as a one-off batch script or a model
retrained every run. The reasoning this entry offers instead, stated as
inference rather than sourced fact, every vendor's architecture is built
around a recurring schedule to attach analysis jobs to, so a model that
genuinely runs once, with no repeated production exposure, has little for
that schedule to monitor.

## 5. Structure

AWS's own documentation gives the clearest sourced breakdown of the
components, enable the endpoint to capture data from incoming requests,
create a baseline from the dataset used to train the model, create a
monitoring schedule specifying what data to collect, how often, how to
analyze it, and which reports to produce, then inspect the reports, which
compare the latest data with the baseline, watching for violations,
metrics, and CloudWatch notifications. This maps onto four component
classes.

The data-quality monitor runs continuously with no label required, AWS's
Deequ-based engine checks statistics, mean, standard deviation, min, max,
unique count, and constraints, data type, completeness, value ranges, on
scheduled processing jobs. The prediction-distribution monitor also runs
without a label, AWS's Evidently-based replacement computes population
stability index and Kolmogorov-Smirnov statistics for every feature,
alerting when the drifted-columns share exceeds a configurable threshold,
and Fiddler independently confirms the same class of metric, Jensen-Shannon
divergence and population stability index. The performance and accuracy
monitor requires a label and runs on the delayed path covered in section
5, merging captured predictions with actual ground truth labels once they
arrive. The operational monitor covers system health rather than model
quality, CloudWatch provides invocation latency, model errors, and
CPU or GPU utilization for SageMaker endpoints, the same class of signal
this catalogue's online-inference entry already covers for the serving
layer itself.

AWS's SageMaker Model Monitor service, the managed offering, carries a
banner on every one of its documentation pages this entry fetched, Amazon
SageMaker Model Monitor is no longer open to new customers, with AWS
naming its recommended replacement composition explicitly, SageMaker AI
MLflow Apps and Evidently AI for statistical drift, an Athena Iceberg data
lake for storage, EventBridge-triggered Lambda for scheduled analysis,
SNS for alerting, QuickSight for dashboards, and CloudWatch for
system-level metrics, with named default thresholds, an F1 score of 0.70,
an accuracy of 0.80, a ROC AUC of 0.75, an alert when more than thirty
percent of features drift, and a default drift threshold of 0.05.

## 7. Dynamics

The join mechanism AWS documents is exact and worth reproducing directly.
To match ground truth labels with captured prediction data, there must be
a unique identifier for each record, and if inferenceId is present in
captured data records, Model Monitor uses it to merge captured data with
ground truth records, falling back to the automatically generated eventId
when the caller did not supply one. AWS's own schema explicitly decouples
label collection time from inference time, the date in the ground truth
storage path is the date when the label is collected, and does not have
to match the date when the inference was generated, a direct
acknowledgment, in the schema's own design, that labels and predictions
arrive on independent clocks.

The full loop, synthesized from the sourced components above, runs as
follows. Production traffic is scored, predictions are logged
continuously with their identifier attached, data-quality and
prediction-distribution checks run on a schedule against those logs with
no label required, ground truth arrives later on its own timeline and is
joined by inferenceId or eventId, performance metrics compute once that
join succeeds, and CloudWatch or an equivalent alerting layer fires on a
threshold breach, at which point AWS's own guidance states the intended
human response, early and proactive detection of these deviations lets you
take corrective actions, like retraining models, auditing upstream
systems, or fixing quality issues.

## 8. Implementation variants

AWS's legacy SageMaker Model Monitor, now closed to new customers, ran
data-quality checks through a Deequ-based engine and model-quality checks
through the merged ground-truth mechanism above, alongside bias-drift and
feature-attribution-drift monitoring. AWS's current recommendation
replaces it with a self-managed, open-source composition, SageMaker AI
MLflow Apps and Evidently AI for the statistical math, an Athena Iceberg
data lake for storage, EventBridge-triggered Lambda for scheduling, SNS
for alerting, QuickSight for dashboards, CloudWatch for operational
metrics, published across seven named reference solutions in AWS's own
sample repository.

Databricks Lakehouse Monitoring is table-native rather than
endpoint-native, computed directly over Delta or Unity Catalog tables
under three named profile types, snapshot, for a full table with a four
terabyte size ceiling, time series, for a table with a timestamp column
profiled across time-based windows, and inference, for a table shaped as a
request log, one row per request, with the model inputs, the
corresponding prediction, and an optional ground-truth label, metrics
computed per model identifier.

Evidently AI, an open-source library confirmed at over forty million
downloads, ships in two modes, a Python library producing local reports,
described as a lightweight visual interface to explore results, and a
self-hosted platform for production monitoring, tracing, storage for AI
application data and evaluation runs, test dataset management, and
dashboards, computed as saved JSON report snapshots that a separate
monitoring service is then launched over, an explicit log-then-analyze
architecture rather than an inline gate.

Fiddler AI is a commercial platform computing drift via Jensen-Shannon
divergence and population stability index, with delayed ground truth as a
named first-class feature and real-time alerting for performance, data
drift, data integrity, and traffic metrics. WhyLabs, once a commercial
vendor, is confirmed no longer operating as a company, with its platform
fully open-sourced into two surviving artifacts, whylogs, described in its
own documentation as the open standard for data logging, offering
privacy-preserving logging and monitoring for AI systems, and langkit, an
open-source toolkit for monitoring large language models. Great
Expectations covers the data-quality leg specifically rather than model
performance, describing itself as the most popular data quality framework
in the world, able to prevent bad data from entering systems or moving
downstream when wired into an orchestrator for continuous monitoring.

## 10. Consequences

Positive. A model's quality is observed continuously rather than assumed,
catching the exact silent, no-exception failure mode Google's own Rules
of Machine Learning names directly, a stale, unmonitored dependency can
decay gradually, sometimes you find tables that are months out of date.
Separating data-quality and prediction-distribution checks, which need no
label, from performance checks, which do, means a real signal is
available immediately even while the slower, label-dependent signal is
still pending.

Negative. The practice adds a standing operational surface, a store of
logged predictions, a scheduling and alerting layer, and, once ground
truth is wired in, a data pipeline carrying real outcome labels back into
the ML system. AWS's own framing of the harm from NOT monitoring, fraud
handlers seeing false positive spikes, loan officers seeing applications
that should have been flagged, planners overestimating demand, is itself
the clearest sourced statement of what is at stake when this surface is
skipped rather than built.

## 11. Failure modes and misuse

Silent decay from an unmonitored dependency is the archetypal failure
mode, Google's Rule 10 names it directly, watch for silent failures, a
stale joined table can decay gradually with nothing crashing to reveal it.

The delayed ground truth problem is a genuine operational bottleneck
rather than a hypothetical inconvenience, AWS names it as the specific
real world difficulty its own inferenceId-based reconciliation design
exists to solve, and a team that treats accuracy monitoring as
instantaneous, rather than accounting for that lag, will trust a stale
green dashboard for exactly as long as the label delay lasts.

This entry could not find an ML-monitoring-specific source naming alert
fatigue or monitoring-the-wrong-metric as explicitly documented failure
modes, distinct from general software alerting discipline. What is
sourced is structural, every platform this entry checked, AWS, Databricks,
Fiddler, keeps operational metrics, latency, error rate, and quality
metrics, drift, accuracy, in architecturally separate systems, which is
consistent with, though it does not directly state, the risk of a team
that wires up only the operational half and mistakes an available,
fast-responding, quietly-wrong model for a healthy one.

## 12. Trade-off matrix

| Approach | Speed to signal | Cost | What it actually proves |
|---|---|---|---|
| Proxy or input monitoring, data quality and prediction distribution | Fast, runs continuously on every logged request or batch with no wait for labels | Low, AWS's own architecture scales compute to zero when idle | Indirect, that the inputs or the shape of the outputs changed, not that the model itself got worse |
| Direct accuracy or performance monitoring | Slow, gated on the real world label latency and the inferenceId join described in section 5 | Higher, needs ground-truth ingestion, storage, and a merge pipeline | Direct, whether predictions matched reality on the exact metric the model is scored on |
| Business-metric monitoring | Slowest, depends on downstream business processes resolving on their own timeline, such as a loan actually defaulting | Highest in cross-team coordination cost, requires a data pipeline back into the ML system from outside it | Most meaningful, whether predictions translated into the outcome the business actually cares about, though this entry found no source giving a concrete, named architecture for this tier specifically, and states that as a reasoned inference from the general shape of the problem rather than a sourced claim |

## 13. Related and incompatible patterns

Drift detection, covered as its own entry in this family, is the specific
statistical technique used within model monitoring to answer one narrow
question, has the distribution of production data shifted since training,
whereas model monitoring is the broader umbrella that also covers
data-quality checks, such as a schema violation or a null-rate spike,
which are not, strictly, distributional drift, and performance monitoring
once labels arrive.

Training-serving skew guard, this family's own entry on that topic,
compares two sources, training and serving, at essentially one point in
time, while model monitoring's drift-detection leg compares one source,
production data, across time, an explicit distinction that entry itself
draws, skew detection is a narrower scope within the broader
model-monitoring umbrella.

Online inference, this family's serving-layer entry, already covers the
operational leg of monitoring, per-instance and per-container latency and
utilization metrics, which model monitoring's operational monitor class
builds on rather than duplicates.

Champion-challenger, this family's deployment-comparison entry, names the
plausible practical connection in its own text, a champion model's
degrading performance, observed through ongoing monitoring, is plausibly
what prompts a team to start evaluating a challenger in the first place,
a relationship that entry itself flags as inferred rather than a directly
sourced requirement, a characterization this entry carries forward rather
than strengthening beyond what the source itself claims.

## 14. Refactoring path in and out

Introducing model monitoring into a system that lacks it starts with the
cheapest, label-free leg first, per AWS's own documented order, enable
data capture on the serving endpoint, establish a baseline from the
training dataset, then add a monitoring schedule that compares live
traffic against that baseline for data-quality and prediction-distribution
checks. The performance-monitoring leg is added once a real ground-truth
pipeline exists, wiring predictions and labels together through the
inferenceId or eventId join described in section 5, since attempting this
leg before a reliable label pipeline exists produces exactly the stale,
overtrusted signal named as a failure mode in section 11.

Removing monitoring, when a model genuinely no longer needs it, for
instance a one-off analysis rather than a recurring production model,
means retiring the monitoring schedule and its alerting wiring while
being deliberate about the data-capture store it leaves behind, since that
store, once it exists, is itself a standing privacy surface per section
17, not something to leave running unattended once its purpose has
ended.

## 16. Observability signals

Model monitoring is itself an observability system, and this entry found
a genuinely interesting, sourced tension worth naming directly rather than
smoothing over. Google's own SRE book chapter on monitoring distributed
systems does not mention machine learning anywhere, and states an explicit
bias against the very kind of automated, threshold-learning approach ML
monitoring tooling implements, we avoid magic systems that try to learn
thresholds or automatically detect causality, a stance in real friction
with Evidently's and SageMaker's own statistical drift tests, which are
exactly that kind of system.

What general SRE practice does contribute cleanly, without friction, is
the operational leg. The same SRE book chapter states the four golden
signals of monitoring are latency, traffic, errors, and saturation, if you
can only measure four metrics of your user-facing system, focus on these
four, which maps directly onto the operational monitor class in section 5
and is the one leg of model monitoring genuinely inherited wholesale from
general software practice rather than being ML-specific. This entry
checked for, and could not verify, a documented connection between the
three pillars of observability, metrics, logs, and traces, and
ML-specific monitoring, and reports that absence honestly rather than
forcing the connection.

## 17. Security and privacy implications

Model monitoring necessarily creates a new, standing store of production
input and output data, and once ground truth is ingested, potentially
sensitive outcome labels too, whether a person defaulted on a loan, for
instance. At least three independent vendors treat this as a first-class
concern rather than an afterthought, AWS's data capture mechanism offers
opt-in encryption for both real-time and batch captured inference data,
Evidently AI lists PII detection among its own built-in evaluation
capabilities, and WhyLabs' surviving open-source artifact, whylogs,
describes itself directly as offering privacy-preserving logging and
monitoring for AI systems.

Retention is a genuine, sourced gap rather than an oversight in this
entry's research. AWS's own data-capture documentation describes storage
location and file format but does not state a retention period or
lifecycle policy for captured predictions or ground-truth labels, checked
directly rather than assumed absent, and Databricks' Lakehouse Monitoring
documentation likewise addresses only the access-control privileges
required to enable profiling, not retention or PII handling. This entry
states that gap plainly, retention policy is conspicuously
under-specified across the platforms checked here, a real open risk worth
naming in any system this pattern is applied to, rather than an invented
concern.

## Code

TypeScript, a monitoring pipeline that logs predictions with an
inference identifier and reconciles them with delayed ground truth,
following the join mechanism in section 7:

```typescript
interface LoggedPrediction {
  inferenceId: string;
  timestamp: number;
  features: Record<string, number>;
  prediction: number;
}

interface GroundTruthRecord {
  inferenceId: string;
  label: number;
}

interface QualityReport {
  matched: number;
  meanAbsoluteError: number;
}

class ModelMonitor {
  private predictions = new Map<string, LoggedPrediction>();
  private baselineMeans: Record<string, number> = {};

  setBaseline(baseline: Record<string, number>): void {
    this.baselineMeans = baseline;
  }

  logPrediction(record: LoggedPrediction): void {
    this.predictions.set(record.inferenceId, record);
  }

  checkDataQuality(threshold: number): string[] {
    const violations: string[] = [];
    const sums: Record<string, number> = {};
    const counts: Record<string, number> = {};
    for (const record of this.predictions.values()) {
      for (const [feature, value] of Object.entries(record.features)) {
        sums[feature] = (sums[feature] ?? 0) + value;
        counts[feature] = (counts[feature] ?? 0) + 1;
      }
    }
    for (const [feature, baselineMean] of Object.entries(this.baselineMeans)) {
      const count = counts[feature] ?? 0;
      if (count === 0) continue;
      const currentMean = sums[feature] / count;
      const delta = Math.abs(currentMean - baselineMean);
      if (delta > threshold) {
        violations.push(feature);
      }
    }
    return violations;
  }

  reconcile(groundTruth: GroundTruthRecord[]): QualityReport {
    let matched = 0;
    let totalError = 0;
    for (const truth of groundTruth) {
      const prediction = this.predictions.get(truth.inferenceId);
      if (!prediction) continue;
      matched += 1;
      totalError += Math.abs(prediction.prediction - truth.label);
    }
    return {
      matched,
      meanAbsoluteError: matched > 0 ? totalError / matched : 0,
    };
  }
}

const monitor = new ModelMonitor();
monitor.setBaseline({ age: 42, income: 55000 });
monitor.logPrediction({
  inferenceId: "req-1",
  timestamp: Date.now(),
  features: { age: 45, income: 61000 },
  prediction: 0.82,
});
console.log(monitor.checkDataQuality(3));
console.log(monitor.reconcile([{ inferenceId: "req-1", label: 1.0 }]));
```

```python
    def set_baseline(self, baseline: dict) -> None:
        self.baseline_means = baseline

    def log_prediction(self, record: LoggedPrediction) -> None:
        self.predictions[record.inference_id] = record

    def check_data_quality(self, threshold: float) -> list:
        violations = []
        for feature, baseline_mean in self.baseline_means.items():
            values = [
                record.features[feature]
                for record in self.predictions.values()
                if feature in record.features
            ]
            if not values:
                continue
            current_mean = mean(values)
            if abs(current_mean - baseline_mean) > threshold:
                violations.append(feature)
        return violations

    def reconcile(self, ground_truth: list) -> QualityReport:
        matched = 0
        total_error = 0.0
        for truth in ground_truth:
            record = self.predictions.get(truth.inference_id)
            if record is None:
                continue
            matched += 1
            total_error += abs(record.prediction - truth.label)
        mae = total_error / matched if matched > 0 else 0.0
        return QualityReport(matched=matched, mean_absolute_error=mae)


if __name__ == "__main__":
    monitor = ModelMonitor()
    monitor.set_baseline({"age": 42, "income": 55000})
    monitor.log_prediction(
        LoggedPrediction("req-1", {"age": 45, "income": 61000}, 0.82)
    )
    print(monitor.check_data_quality(3))
    print(monitor.reconcile([GroundTruthRecord("req-1", 1.0)]))
```

Go, the same monitor shape with an explicit alerting hook, following the
alerting layer described in section 5:

```go
package main

import (
	"fmt"
	"math"
)

type LoggedPrediction struct {
	InferenceID string
	Features    map[string]float64
	Prediction  float64
}

type GroundTruthRecord struct {
	InferenceID string
	Label       float64
}

type QualityReport struct {
	Matched            int
	MeanAbsoluteError  float64
}

type ModelMonitor struct {
	predictions   map[string]LoggedPrediction
	baselineMeans map[string]float64
}

func NewModelMonitor() *ModelMonitor {
	return &ModelMonitor{
		predictions:   make(map[string]LoggedPrediction),
		baselineMeans: make(map[string]float64),
	}
}

func (m *ModelMonitor) SetBaseline(baseline map[string]float64) {
	m.baselineMeans = baseline
}

func (m *ModelMonitor) LogPrediction(record LoggedPrediction) {
	m.predictions[record.InferenceID] = record
}

func (m *ModelMonitor) CheckDataQuality(threshold float64) []string {
	violations := []string{}
	for feature, baselineMean := range m.baselineMeans {
		sum := 0.0
		count := 0
		for _, record := range m.predictions {
			if value, ok := record.Features[feature]; ok {
				sum += value
				count++
			}
		}
		if count == 0 {
			continue
		}
		currentMean := sum / float64(count)
		if math.Abs(currentMean-baselineMean) > threshold {
			violations = append(violations, feature)
		}
	}
	return violations
}

func (m *ModelMonitor) Reconcile(groundTruth []GroundTruthRecord) QualityReport {
	matched := 0
	totalError := 0.0
	for _, truth := range groundTruth {
		record, ok := m.predictions[truth.InferenceID]
		if !ok {
			continue
		}
		matched++
		totalError += math.Abs(record.Prediction - truth.Label)
	}
	mae := 0.0
	if matched > 0 {
		mae = totalError / float64(matched)
	}
	return QualityReport{Matched: matched, MeanAbsoluteError: mae}
}

func main() {
	monitor := NewModelMonitor()
	monitor.SetBaseline(map[string]float64{"age": 42, "income": 55000})
	monitor.LogPrediction(LoggedPrediction{
		InferenceID: "req-1",
		Features:    map[string]float64{"age": 45, "income": 61000},
		Prediction:  0.82,
	})
	fmt.Println(monitor.CheckDataQuality(3))
	fmt.Println(monitor.Reconcile([]GroundTruthRecord{{InferenceID: "req-1", Label: 1.0}}))
}
```
