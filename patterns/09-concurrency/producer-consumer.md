## 1. Name, aliases, and lineage

The canonical name is Producer-Consumer, also called the Bounded Buffer problem
or the Producer-Consumer Queue. Edsger Dijkstra posed the underlying
synchronization problem in his 1965 paper on cooperating sequential processes,
where he introduced semaphores specifically to solve the case of one process
filling a buffer while another drains it without either process racing the
other or overrunning the buffer's capacity. The pattern as a reusable
architectural building block, distinct from the raw semaphore-based proof, is
documented in Douglas Schmidt, Michael Stal, Hans Rohnert, and Frank Buschmann,
Pattern-Oriented Software Architecture Volume 2. Patterns for Concurrent and
Networked Objects, Wiley, 2000, where it appears embedded inside the
Half-Sync/Half-Async pattern's queueing layer and the Monitor Object pattern's
worked examples, rather than as a standalone chapter. Most concurrent
programming textbooks since, including Goetz et al., Java Concurrency in
Practice, Addison-Wesley, 2006, chapter 5, treat it as a named idiom rather
than a formal Gang of Four style pattern, because its structure is small enough
to be a single data structure, a blocking queue, rather than a multi-class
collaboration. Some texts use "Bounded Buffer" specifically for the
capacity-limited variant and reserve "Producer-Consumer" for the general shape
including unbounded queues, but the two names are used interchangeably in most
production discussion, and this entry treats them as one pattern with a
capacity parameter.

## 2. Problem and context

A piece of work is generated by one part of a system at a rate, and shape, that
does not match the rate or shape at which another part of the system can
consume it. A web server accepts HTTP connections faster in bursts than a
downstream image-resizing routine can resize images. A sensor emits readings
on a fixed clock while the analytics job that consumes them sometimes pauses
for a slow database write. A logging call happens on the hot path of every
request while writing that line to disk takes milliseconds the hot path cannot
afford. In every one of these cases, calling the consumer directly from the
producer's thread of control ties the producer's speed to the consumer's
speed, and any variance in one becomes latency or failure in the other. The
producer either blocks on a slow consumer, defeating the reason the producer
existed as a separate concern, or the producer must run on its own thread and
somehow hand its output to the consumer's thread safely, without corrupting
shared memory and without either side polling in a busy loop.

The context in which this problem arises has three ingredients present
together. First, work items are produced and consumed by logically separate
activities that benefit from running concurrently, meaning there is a real
reason to decouple them rather than call one from the other synchronously.
Second, the rates of production and consumption differ, or vary
unpredictably, so a direct handoff would stall the faster side. Third, the
work items themselves are self-contained enough to be queued, meaning a
producer can finish generating one item without needing an answer back from
the consumer before generating the next. Where any of these three is absent,
for example where the two sides always run at matched speed, or where the
producer genuinely needs a synchronous reply before proceeding, the pattern is
not a fit, and the applicability list in dimension 4 makes that explicit.

## 3. Forces

The central force is decoupling versus coordination cost. A shared queue
between a producer and a consumer removes the requirement that both run in
lockstep, which is the entire value of the pattern, but that queue is itself a
piece of shared mutable state that must be protected against concurrent
access, and every protection mechanism, whether a lock, a semaphore, or a
lock-free ring buffer, has a cost in CPU cycles and code complexity that a
direct function call does not pay.

A second force is memory bound against latency. An unbounded queue never makes
the producer wait, so producer-side latency is minimal and predictable, but an
unbounded queue in front of a permanently slower consumer grows without limit
and eventually exhausts memory, which converts a slow-consumer problem into an
out-of-memory crash. A bounded queue caps memory, but a bounded queue that
fills makes the producer choose between blocking, which reintroduces
coupling, and dropping the item, which loses data. There is no setting of the
capacity number that removes this trade-off, only a choice of which failure
mode the system prefers under sustained overload.

A third force is fairness and ordering against throughput. A single shared
queue with multiple producers and multiple consumers gives strict FIFO
ordering relative to enqueue time under most implementations, which many
callers rely on implicitly, but a single queue is also a single point of lock
contention, and past a certain number of concurrent producers and consumers
the lock itself becomes the bottleneck. Sharding the queue into multiple
partitions, the approach Kafka takes at scale, restores throughput at the cost
of only guaranteeing order within a partition rather than globally, and the
partitioning key then becomes a design decision with its own consequences for
skew.

A fourth force is backpressure signaling against producer simplicity. A
bounded queue that blocks the producer when full is implicitly propagating
backpressure one hop upstream, which is often exactly what a well-behaved
system needs, but it means the producer's code must be written to tolerate
blocking, which is a different programming model than fire-and-forget, and it
means a slow consumer can eventually stall every upstream producer that
shares the same queue, turning a local slowdown into a system-wide one unless
the topology is designed with that propagation in mind.

The pattern favors decoupling and bounded memory use over minimal coordination
overhead and over guaranteed zero producer latency, and it explicitly
sacrifices the simplicity of a direct call in exchange for independent
scheduling of the two sides.

## 4. Applicability and non-applicability

Reach for Producer-Consumer when work items are naturally discrete and
self-contained, when production and consumption rates differ or vary, when the
producer should not be blocked waiting for the consumer to finish processing
the specific item it handed off, when multiple producers or multiple
consumers need to share one workload fairly, or when a system needs a single
point at which to apply backpressure, rate limiting, or batching between two
otherwise independent components. It is a strong fit for I/O staging, where a
fast in-memory producer feeds a slow disk or network consumer, for event
buses inside a single process, for task queues that spread work across a
worker pool, and for any pipeline stage boundary where the two stages should
be sized and deployed independently of each other.

Do not reach for it when the producer needs an immediate, synchronous answer
from the consumer before it can proceed, because a queue turns that into a
request-response protocol layered awkwardly on top of a one-way channel,
better solved with a direct call, a Future, or a request-response pattern like
Half-Sync/Half-Async's synchronous layer. Do not reach for it when there is
exactly one producer and one consumer running at matched, predictable speed
with no burstiness, because the queue adds coordination overhead for no
decoupling benefit and a direct function call or a single-slot handoff is
simpler and faster. Do not reach for it when ordering across the entire
system must be strictly total and multiple producers exist, because a queue
only guarantees FIFO relative to its own enqueue order and reconciling that
with a global order requires an additional sequencing mechanism, as the
LMAX Disruptor's single-writer principle addresses directly (LMAX Exchange,
"Disruptor", https://lmax-exchange.github.io/disruptor/, verified 2026-08-02).
Do not reach for an unbounded queue when the consumer can be permanently
slower than the producer under realistic load, because that configuration
converts a design pattern into a slow-motion memory leak, and do not reach for
this pattern at all when the two sides can simply be merged into one
sequential piece of code with no concurrency requirement, because a queue
introduces a genuine failure surface, memory use, and reasoning cost that a
straight-line function call does not have.

## 5. Structure

The pattern has three participants. The Producer is the component that
generates work items and calls a put or enqueue operation on the shared
buffer; it does not know or care which consumer, if any, will eventually
process an item, and it does not block on anything except the buffer itself
being full when the buffer is bounded. The Consumer is the component that
calls a take or dequeue operation on the shared buffer and processes whatever
item it receives; it does not know or care which producer generated the
item, and it blocks on the buffer being empty rather than busy-polling. The
Bounded Buffer, sometimes called the Queue, is the shared, thread-safe
data structure that mediates between them; it owns the synchronization state,
typically a lock paired with two condition variables, one signaled when an
item becomes available and one signaled when space becomes available, and it
is the only participant that touches raw synchronization primitives directly.
In a multi-producer, multi-consumer configuration, there are N Producer
instances and M Consumer instances all sharing exactly one Bounded Buffer
instance, and the buffer's internal locking must correctly serialize access
from all N+M threads.

## 7. Dynamics

At runtime, a producer thread calls put with a completed item. Inside the
buffer's implementation, the calling thread acquires the buffer's internal
lock, checks whether the current size equals the configured capacity, and if
so waits on the notFull condition variable, releasing the lock while it
waits. Once space exists, the thread appends the item to the internal
storage, increments the size, signals the notEmpty condition variable to wake
any consumer that may be waiting, and releases the lock. Symmetrically, a
consumer thread calls take, acquires the same lock, checks whether the
current size is zero, and if so waits on the notEmpty condition variable.
Once an item exists, the thread removes it from the front of the internal
storage, decrements the size, signals notFull to wake any waiting producer,
releases the lock, and returns the item to the caller for processing outside
the lock. The critical property is that the item is processed by the
consumer after the lock has been released, so a slow consumer processing one
item does not hold the buffer's lock and does not block other producers or
consumers from enqueueing or dequeueing concurrently; only the brief
enqueue or dequeue operation itself is serialized.

```
Producer thread                Buffer (locked region)              Consumer thread
     |                               |                                    |
     | put(item) ------------------>|                                    |
     |                          acquire lock                              |
     |                          size == capacity? --wait on notFull-->    |
     |                          (blocks here if full)                    |
     |                          append item                               |
     |                          size++                                    |
     |                          signal notEmpty ------------------------> | (wakes if waiting)
     |                          release lock                              |
     | <---------------------------- return                               |
     |                               |                                    |
     |                               |                acquire lock <------| take()
     |                               |                size == 0? --wait on notEmpty-->
     |                               |                (blocks here if empty)
     |                               |                remove item
     |                               |                size--
     |                               |<--------------- signal notFull
     |                               |                release lock
     |                               |                return item -------> process(item)
```

## 8. Implementation variants

The lock-and-two-condition-variables variant described above is the classic
POSA2 monitor-based implementation and is what Java's ArrayBlockingQueue and
LinkedBlockingQueue provide directly through their put and take methods,
where BlockingQueue implementations are, in the JDK's own words, "designed to
be used primarily for producer-consumer queues" and can "safely be used with
multiple producers and multiple consumers" (Oracle, "BlockingQueue (Java SE
21 & JDK 21)",
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/BlockingQueue.html,
verified 2026-08-02). A second variant replaces the explicit lock and
condition variables with an unbuffered or buffered channel, where the runtime
scheduler itself implements the blocking semantics; Go's channels are the
best-known example, and Effective Go documents both the unbuffered case,
where "receivers always block until data is available" and the buffered case
used as a bounded work-limiting mechanism (The Go Authors, "Effective Go",
https://go.dev/doc/effective_go#channels, verified 2026-08-02). A third
variant is the semaphore-pair implementation closest to Dijkstra's original
formulation, using a counting semaphore initialized to the buffer capacity to
represent free slots and a second counting semaphore initialized to zero to
represent filled slots, with a mutex protecting the actual array indices;
this is the textbook construction still taught because it makes the
bounded-buffer invariant explicit as two numbers rather than hidden inside a
condition-variable predicate. A fourth variant, used when maximum throughput
under a single writer matters more than general-purpose flexibility, is a
lock-free ring buffer with a pre-allocated fixed-size array and atomic
sequence counters instead of a lock at all; the LMAX Disruptor is the
reference implementation of this style, built because "performance testing
showed that using queues to pass data between stages of the system was
introducing latency" in a conventional lock-based queue under LMAX's trading
workload (LMAX Exchange, "Disruptor",
https://lmax-exchange.github.io/disruptor/, verified 2026-08-02). A fifth
variant moves the buffer out of process memory entirely into a durable,
network-accessible broker, which is the shape taken by message-queue systems
like RabbitMQ and by log-structured systems like Kafka, where "producers and
consumers are fully decoupled and agnostic of each other" and "producers
never need to wait for consumers" (Apache Software Foundation, "Apache Kafka.
Introduction", https://kafka.apache.org/intro, verified 2026-08-02); this
variant trades in-process speed for durability, cross-process fan-out, and
survival of consumer or producer restarts. A sixth, language-idiomatic
variant uses cooperative coroutines rather than OS threads, where the
"producer" and "consumer" are async generator functions and the queue is an
asyncio.Queue whose put and get are coroutines that yield control rather than
blocking a thread, appropriate when the workload is I/O-bound rather than
CPU-bound and thousands of concurrent producers or consumers would be too
many OS threads to run efficiently.

## 9. Known production uses

Java's java.util.concurrent.BlockingQueue family, specifically
ArrayBlockingQueue, LinkedBlockingQueue, and SynchronousQueue, is the
producer-consumer primitive underlying java.util.concurrent.ThreadPoolExecutor's
work queue, meaning every standard Java thread pool is a producer-consumer
system where submit calls are producers and pool threads are consumers
(Oracle, "BlockingQueue (Java SE 21 & JDK 21)",
https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/BlockingQueue.html,
verified 2026-08-02).

Python's standard library queue.Queue module implements, in its own
documentation's words, "multi-producer, multi-consumer queues" specifically
because they are "especially useful in threaded programming for safely
exchanging information between multiple threads," and the module's canonical
worked example is a worker-thread pool draining a shared Queue (Python
Software Foundation, "queue. A synchronized queue class",
https://docs.python.org/3/library/queue.html, verified 2026-08-02).

Go's standard library channel primitive is used throughout the language's
own documentation and the wider ecosystem as the idiomatic producer-consumer
mechanism, with Effective Go's own worked example using a buffered channel as
a bounded work queue read by a fixed pool of handler goroutines (The Go
Authors, "Effective Go", https://go.dev/doc/effective_go#channels, verified
2026-08-02).

Apache Kafka is a production message broker built around the
producer-consumer separation at the scale of an entire distributed system,
where the broker's own documentation states that producers publish events and
consumers subscribe to and process them, and that this decoupling is, in the
broker's own words, "a key design element" behind the large scale Kafka is
built to handle (Apache Software Foundation, "Apache Kafka. Introduction",
https://kafka.apache.org/intro, verified 2026-08-02).

The LMAX Disruptor is a production, open-source, lock-free implementation of
the pattern originally built inside LMAX's financial trading exchange to
replace a conventional lock-based queue after "performance testing showed
that using queues to pass data between stages of the system was introducing
latency" (LMAX Exchange, "Disruptor",
https://lmax-exchange.github.io/disruptor/, verified 2026-08-02), and it is
now used as a library independent of LMAX by other low-latency systems that
need the same single-writer, cache-friendly ring buffer design.

## 10. Consequences

The positive consequences are, first, genuine decoupling of production rate
from consumption rate, so a burst on the producer side is absorbed by the
buffer rather than propagating as latency to every consumer call; second,
independent sizing of the two sides, because the number of producer threads
and the number of consumer threads can each be tuned separately against the
queue without touching the other side's code; third, a natural point to
apply cross-cutting concerns such as metrics, rate limiting, batching, or
priority ordering, because every item passes through one well-defined
chokepoint; fourth, simplified reasoning about thread safety for the rest of
the system, because once the buffer itself is proven correct, the producer
and consumer code can be written as if they were single-threaded, with the
only shared state being the buffer.

The negative consequences are, first, an added memory cost proportional to
queue depth, which for a bounded queue is a fixed and known cost but for an
unbounded queue is an unbounded and unknown one; second, an added latency
cost for every item, because it must be enqueued and dequeued rather than
handled inline, which matters in latency-sensitive paths even when the
constant overhead is small; third, a new failure mode where a stalled
consumer causes a bounded queue to fill and every producer to block, which
can silently propagate a local outage into a much larger one if the topology
is not designed to isolate that blast radius; fourth, an ordering guarantee
that is weaker than most callers assume once more than one producer or more
than one consumer is involved, because FIFO order is guaranteed only relative
to enqueue time on a single queue, not relative to wall-clock time across
multiple producers, and not preserved at all once a queue is sharded across
partitions for throughput.

## 11. Failure modes and misuse

Symptom. Memory usage grows steadily and eventually the process is killed
by the operating system's out-of-memory handler, or the process throws an
allocation failure. Cause. An unbounded queue was chosen in front of a
consumer that is, under some realistic load condition, slower on average than
the producer, so the queue's size trends upward without bound over time
rather than reaching a steady state. Fix. Replace the unbounded queue
with a bounded one sized to the largest burst the system needs to absorb, and
decide explicitly, as a design decision rather than a default, what happens
when the buffer is full, whether that is blocking the producer, rejecting
the item, or dropping the oldest item, because one of those three must happen
and only an explicit choice avoids the implicit choice of unbounded growth.

Symptom. The whole system appears to hang under moderate load even though
CPU usage is low and no exception is thrown. Cause. A bounded queue's
producer-side block, intended as backpressure to one upstream component, has
propagated across multiple hops of a pipeline, because each stage's producer
is itself the previous stage's consumer, and a single slow terminal stage has
stalled every stage feeding into it. Fix. Add a timeout to blocking put
calls where indefinite backpressure propagation is not acceptable, and
monitor queue depth at every stage so the specific stalled stage is visible
rather than inferred from a system-wide symptom, since dimension 16 covers
exactly this signal.

Symptom. Items are processed out of the order they were produced, and a
downstream component that relies on ordering produces incorrect results.
Cause. Multiple producer threads enqueue concurrently, or the queue has
been sharded into multiple partitions for throughput, and the caller assumed
a single global FIFO order that the implementation never actually guaranteed
across more than one producer or more than one partition. Fix. Either
route items that must stay ordered relative to each other through a single
producer and a single partition, using a partitioning key derived from the
entity whose order matters, as Kafka's partition-key model does, or remove
the ordering assumption from the downstream component and make it tolerant
of arbitrary interleaving, whichever is cheaper for the specific system.

Symptom. Under a spike of concurrent producer and consumer threads,
throughput plateaus or drops even though more threads were added specifically
to increase throughput. Cause. A single shared queue with one internal
lock has become the point of contention; every producer and consumer must
briefly hold that lock, and past a certain thread count the time spent
waiting for the lock exceeds the time spent doing useful work, an effect that
worsens as more threads compete for the same lock. Fix. Either shard the
work across multiple independent queues, accepting the weaker per-shard
ordering guarantee described above, or move to a lock-free implementation
such as a ring buffer, which is precisely the motivation LMAX documented for
building the Disruptor after finding lock-based queueing introduced latency
under their workload.

Symptom. An item that was successfully dequeued by a consumer is lost
entirely when the consumer process crashes mid-processing, and the item is
never seen again anywhere in the system. Cause. An in-memory bounded
buffer, whether the language's built-in blocking queue or a custom ring
buffer, holds items only in process memory with no durability, so a
dequeue-then-crash sequence loses the item permanently, which is acceptable
for many workloads but is a silent data-loss bug for any workload that
assumed at-least-once delivery. Fix. For workloads that require
surviving a consumer crash, use a durable broker variant such as Kafka or
RabbitMQ, where the item is not considered consumed until the consumer
explicitly acknowledges it, and an unacknowledged item is redelivered.

## 12. Trade-off matrix

| Force | Producer-Consumer (bounded blocking queue) | Direct synchronous call | Half-Sync/Half-Async | Active Object |
|---|---|---|---|---|
| Decouples producer rate from consumer rate | Yes, that is its purpose | No, caller and callee run in lockstep | Yes, the queueing layer is a producer-consumer buffer | Yes, per-object |
| Producer-side latency for one item | Low, one enqueue operation | Includes full consumer processing time | Low on the async side | Low, one scheduler enqueue |
| Memory bound under sustained overload | Bounded if capacity is set, unbounded otherwise | None, no buffering exists | Same as its internal producer-consumer layer | Same as its internal scheduler queue |
| Cross-process durability | No, in-memory unless a broker variant is used | N/A | No, in-process only | No, in-process only |
| Ordering guarantee | FIFO per producer or per partition only | Total, by construction of a single call stack | Same as its internal queue | Per-object method call order preserved |
| Coordination overhead vs a bare function call | One lock acquisition or one channel operation per item | None | Same as underlying producer-consumer plus a sync/async boundary | One scheduler enqueue plus a future resolution |
| Best fit | Rate mismatch between two concurrent components | Matched-speed, tightly coupled logic that needs an immediate answer | A service that must expose both a synchronous API and an asynchronous internal pipeline | A single object whose method calls must be serialized without blocking callers |

## 13. Related and incompatible patterns

Producer-Consumer is the concrete mechanism most often used inside the
Half-Sync/Half-Async pattern's queueing layer, where a synchronous-facing API
enqueues work that an asynchronous processing layer drains; the two patterns
compose directly, with Half-Sync/Half-Async naming the overall
synchronous-to-asynchronous boundary and Producer-Consumer providing the
buffer that implements it. It is also the mechanism most often used inside
Active Object, where each method call on the active object is turned into a
request enqueued on the object's own internal producer-consumer buffer and
executed later by a dedicated scheduler thread, meaning Active Object is a
specific, per-object application of Producer-Consumer rather than a
competing alternative to it. Producer-Consumer's buffer itself is frequently
implemented as a Monitor Object, since a monitor's combination of a mutex and
one or more condition variables is exactly the mechanism the bounded buffer
needs internally, making Monitor Object the implementation vehicle rather than
a design-level relative. It composes with Thread-Safe Interface at the
buffer's boundary, since the buffer's public put and take methods are
themselves an instance of that pattern, presenting a safe, blocking interface
while hiding the internal lock and condition variable machinery from
callers. Reactor and Proactor are complementary rather than competing,
because both are commonly used on the producer side to turn incoming I/O
events into items placed on a producer-consumer queue for a separate worker
pool to process, decoupling the event-detection loop from processing logic that may run
slowly. Leader-Followers is a genuine alternative
rather than a composition partner in the specific case where the goal is a
thread pool draining a shared event source, because Leader-Followers
achieves that goal without a central queue at all, having threads take turns
being the one thread that waits directly on the event source, which removes
the queue's memory cost and one hop of latency at the price of a more
complex leadership-handoff protocol; a system choosing between the two is
choosing between queue-based decoupling and direct, rotating access to the
source.

## 14. Refactoring path in and out

To introduce this pattern into code that currently calls a slow operation
directly from a hot path, first identify the exact call being made
synchronously and confirm its result, if any, is not needed immediately by
the caller, since a caller that needs an immediate answer is not a candidate
for this pattern without also introducing a Future or callback. Next,
introduce a bounded queue sized to a first estimate of the burst the system
must absorb, choosing a small, conservative capacity rather than an
unbounded one so that a sizing mistake fails loudly as producer blocking
rather than silently as memory growth. Move the slow operation itself into a
dedicated worker function that loops on the queue's take or equivalent
blocking-receive call and executes the operation on whatever item it
receives. Replace the original direct call site with an enqueue call to the
new queue. Start one or more worker threads or goroutines running the
worker function, sized to the available concurrency budget, then measure
queue depth and producer block time under representative load and adjust
capacity and worker count from the measurement rather than from a guess.
Finally, decide and implement the full-buffer policy explicitly, whether
that is a bounded block, a timeout, or a drop, because leaving the default
in place without deciding is the single most common source of the failure
modes in dimension 11.

To remove this pattern once it stops earning its place, most often because
the workload turned out to be matched-speed and the queue is adding latency
with no decoupling benefit, first confirm through measurement, not
assumption, that producer and consumer rates are genuinely matched under
production load, since removing the buffer under a mistaken assumption
reintroduces the original coupling problem. Then replace the enqueue call
with a direct call to the worker logic, inline the worker function at the
call site or leave it as a plain function call rather than a queue-consuming
loop, and remove the now-unused queue and worker thread lifecycle code. This
is the Inline Method direction of a standard refactoring, and it should be
done incrementally, one call site at a time, with the queue-based version
kept available behind a feature flag until the direct-call version has run
under production load without regressing the specific latency or coupling
metric that originally motivated the pattern's removal.

## 15. Testing and verification

The buffer's core invariants, that it never reports empty when a put has
occurred without a matching take, and that it never exceeds its configured
capacity, are unit-testable directly with a single-threaded test that calls
put and take in a controlled sequence and asserts on size and on the
returned items, without needing any actual concurrency to exercise the
sequential logic. The genuinely concurrent behavior, specifically that a
consumer blocked on an empty buffer is correctly woken by a producer's put
and that a producer blocked on a full buffer is correctly woken by a
consumer's take, is harder to test deterministically because it depends on
thread scheduling; the standard technique is to start the blocking call on a
separate thread, use a short, bounded wait with a timeout to confirm the
call is genuinely blocked rather than merely slow, then perform the
unblocking operation on the test's main thread and assert the blocked call
returns within a second bounded timeout, treating a timeout expiry itself as
a test failure rather than a flaky pass. Producer and consumer logic
themselves become easier to test in isolation once this pattern is in place,
because a producer can be tested by asserting on what it enqueues without
needing a real consumer running, and a consumer can be tested by feeding it
a queue pre-populated with fixture items and asserting on its processing
without needing a real producer, which is a direct benefit of the decoupling
this pattern provides. What becomes harder to test is any end-to-end timing
or ordering property across the whole pipeline, because the queue
deliberately introduces non-determinism in exactly when an item is
processed relative to wall-clock time, so end-to-end tests should assert on
eventual outcomes with a bounded wait rather than on precise timing, and
tests that need strict ordering across multiple producers should route all
items through a single producer in the test to remove the non-determinism
the pattern otherwise permits.

## 16. Observability signals

Current queue depth, meaning the number of items currently enqueued but not
yet dequeued, is the single most informative metric for this pattern and
should be recorded as a gauge sampled continuously rather than only logged
on state changes, because a queue depth trending upward over minutes to
hours is the earliest visible sign of the sustained-overload failure mode in
dimension 11 well before memory pressure or blocking becomes user-visible. A
healthy instance shows queue depth fluctuating within a bounded range that
tracks short-term load variation and returns toward zero, or toward a small
steady-state value, between bursts; a failing instance shows queue depth on
a sustained upward trend with no return to baseline, or shows queue depth
pinned at the configured capacity for an extended period, which indicates
producers are being blocked. Producer block time, meaning the time a
producer's put call spends waiting for space before it returns, and
consumer wait time, meaning the time a consumer's take call spends waiting
for an item before it returns, should both be recorded as histograms;
sustained non-zero producer block time under normal load indicates the
consumer side is undersized relative to the producer side, while sustained
non-zero consumer wait time is normal and expected during quiet periods and
only becomes a concern if it drops to zero under load that should have some
idle time, which can indicate the consumer side is undersized enough that
producers are always waiting instead. Item age, meaning the time between an
item's enqueue and its dequeue, should be recorded per item where the
processing cost of doing so is acceptable, because it directly measures the
latency this pattern adds to the end-to-end path and is the metric a
latency-sensitive caller of the whole pipeline actually cares about, as
distinct from queue depth, which measures backlog but not the specific
delay any one item experienced.

## 17. Security and privacy implications

A bounded queue used for backpressure is itself a form of denial-of-service
mitigation, because it caps how much unprocessed work an attacker can force
the system to hold in memory by simply submitting requests faster than they
can be processed, converting an unbounded memory-exhaustion attack surface
into a bounded one whose worst case is producer-side blocking or item
rejection rather than an out-of-memory crash; choosing an unbounded queue
therefore reintroduces this attack surface and should be treated as a
deliberate risk decision, not a default. Where queue items themselves carry
sensitive data, such as personal information awaiting processing or
credentials awaiting validation, that data persists in process memory for
the entire time the item sits in the queue, which extends the window during
which a memory dump, a core dump written to disk after a crash, or a
debugging tool attached to the process could expose it beyond the brief
window a direct synchronous call would have created; systems handling
sensitive data through a queue should consider whether the item can be
minimized to a reference or identifier rather than the sensitive payload
itself, with the payload retrieved from an access-controlled store only at
the point of actual processing. Where the queue is implemented as an
external, durable broker rather than an in-process buffer, as with Kafka or
RabbitMQ, the security surface expands to include the broker's own network
exposure, authentication, and at-rest encryption, and the broker becomes a
place sensitive data may persist on disk for a retention period configured
independently of the application's own data-retention policy, which is a
distinct and separately-auditable concern from the in-process variants
covered elsewhere in this entry.

## Code examples

### TypeScript

```typescript
class BoundedBuffer<T> {
  private items: T[] = [];
  private waitingConsumers: ((v: T) => void)[] = [];
  private waitingProducers: (() => void)[] = [];

  constructor(private capacity: number) {}

  async put(item: T): Promise<void> {
    while (this.items.length >= this.capacity) {
      await new Promise<void>((resolve) => this.waitingProducers.push(resolve));
    }
    this.items.push(item);
    const consumer = this.waitingConsumers.shift();
    if (consumer) consumer(this.items.shift() as T);
  }

  async take(): Promise<T> {
    if (this.items.length === 0) {
      return new Promise<T>((resolve) => this.waitingConsumers.push(resolve));
    }
    const item = this.items.shift() as T;
    const producer = this.waitingProducers.shift();
    if (producer) producer();
    return item;
  }
}

async function main(): Promise<void> {
  const buffer = new BoundedBuffer<number>(3);

  async function producer(id: number): Promise<void> {
    for (let i = 0; i < 5; i++) {
      await buffer.put(id * 100 + i);
    }
  }

  async function consumer(id: number, count: number): Promise<void> {
    for (let i = 0; i < count; i++) {
      const item = await buffer.take();
      console.log(`consumer ${id} got ${item}`);
    }
  }

  await Promise.all([producer(1), producer(2), consumer(1, 5), consumer(2, 5)]);
}

main();
```

### Python

```python
import threading
import queue
import time

def producer(q: queue.Queue, producer_id: int, count: int) -> None:
    for i in range(count):
        item = f"p{producer_id}-item{i}"
        q.put(item)
        time.sleep(0.01)

def consumer(q: queue.Queue, consumer_id: int, total_items: int, done: threading.Event) -> None:
    processed = 0
    while processed < total_items:
        item = q.get()
        processed += 1
        q.task_done()
    done.set()

def main() -> None:
    buffer: queue.Queue = queue.Queue(maxsize=5)
    total = 10
    done = threading.Event()

    consumer_thread = threading.Thread(target=consumer, args=(buffer, 1, total, done))
    consumer_thread.start()

    producer_threads = [
        threading.Thread(target=producer, args=(buffer, pid, 5))
        for pid in (1, 2)
    ]
    for t in producer_threads:
        t.start()
    for t in producer_threads:
        t.join()

    done.wait(timeout=5)
    consumer_thread.join(timeout=1)
    print("all items processed" if done.is_set() else "timed out")

if __name__ == "__main__":
    main()
```

### Go

```go
package main

import (
	"fmt"
	"sync"
)

func producer(id int, out chan<- int, wg *sync.WaitGroup) {
	defer wg.Done()
	for i := 0; i < 5; i++ {
		out <- id*100 + i
	}
}

func consumer(id int, in <-chan int, wg *sync.WaitGroup) {
	defer wg.Done()
	for item := range in {
		fmt.Printf("consumer %d got %d\n", id, item)
	}
}

func main() {
	buffer := make(chan int, 3)

	var producers sync.WaitGroup
	producers.Add(2)
	go producer(1, buffer, &producers)
	go producer(2, buffer, &producers)

	var consumers sync.WaitGroup
	consumers.Add(2)
	go consumer(1, buffer, &consumers)
	go consumer(2, buffer, &consumers)

	producers.Wait()
	close(buffer)
	consumers.Wait()
}
```
