# Static Content Hosting

## 1. Name, aliases, and lineage

The pattern goes by several names depending on which layer of the stack the
speaker is standing in. Cloud vendors call it "static website hosting", the
term Amazon Web Services uses for the S3 bucket-as-web-server feature,
described in the AWS S3 user guide, verified 2026-08-02,
https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteHosting.html.
Frontend engineers who grew up with the 2015 to 2020 wave of build-then-deploy
tooling call it "JAMstack hosting", after the JavaScript, APIs, and Markup
acronym coined to describe sites that ship pre-built HTML instead of rendering
on a server per request. Infrastructure engineers who care about the wire
protocol call it "static asset origin plus CDN", because the pattern is really
two composed things, an origin that stores immutable bytes, and a content
delivery network that caches and serves those bytes from many points of
presence close to the reader.

There is no single named inventor. Unlike Gang of Four patterns, this pattern
was not proposed in a paper and then adopted. It emerged from the collision of
two older ideas that existed independently for years before anyone treated
their combination as a first-class hosting strategy. The first idea is object
storage as a durable, cheap place to keep bytes, exemplified by Amazon S3,
launched in 2006. The second idea is the content delivery network, commercial
CDNs tracing back to Akamai Technologies, founded in 1998 by Daniel Lewin, F.
Thomson Leighton, and colleagues out of MIT research into consistent hashing,
built specifically to route around what its own history describes as the
"middle-mile bottleneck of the Internet" that congested the web as commercial
traffic exploded in the late 1990s (Wikipedia, Akamai Technologies, verified
2026-08-02, https://en.wikipedia.org/wiki/Akamai_Technologies). Object storage
gave engineers a place to put files without running a server. CDNs gave those
files a fast, globally distributed path to a reader's browser. Static content
hosting, as a named pattern, is the recognition that for an entire class of
applications, the two together replace the application server outright.

A companion name worth distinguishing from this pattern is "static site
generator", which is a build-time tool such as Jekyll, Hugo, Next.js static
export, Astro, or Eleventy, that produces the HTML this pattern serves. The
generator is upstream of the pattern. This entry is about what happens to the
generated bytes after the build finishes, not about how the bytes were
produced.

## 2. Problem and context

A team is building a website, a documentation portal, a marketing page, a
single-page application, or the client half of a larger system, and the
content does not need to change per request. The HTML, CSS, JavaScript,
images, and fonts that make up the page are identical whether the tenth reader
or the ten-millionth reader requests them today. The only thing that varies
between requests is which reader is asking and where in the world they are
asking from.

Traditionally this workload was served by running a web server process,
Apache or nginx, on a machine the team owned or rented, reading files off
local disk for every request. That server had to be provisioned for peak load
even though most of its life is spent idle, had to be patched, had to be
geographically somewhere, which meant every reader on the far side of the
planet paid the round-trip latency to reach that somewhere, and represented a
single point of failure that, if it went down, took the entire site down with
it.

The problem this pattern solves is precisely that mismatch, a workload with
no per-request computation, no per-request state, and a read-heavy, globally
distributed audience being served by infrastructure designed for workloads
that do have per-request computation and state. The context in which this
pattern is the right answer requires three things to be true simultaneously.
The content is the same for every reader, or varies only by parameters that
can be resolved at the edge, such as a locale header or a signed cookie,
rather than by a database lookup. The content changes on a build or publish
cadence measured in minutes or longer, not on every write. And the audience
is large enough, or distributed enough, that the latency and reliability
benefits of edge caching outweigh the operational simplicity of a single
server.

## 3. Forces

**Latency versus freshness.** Caching content at many edge locations close to
readers is the entire point of the pattern, and caching is fundamentally in
tension with freshness. The longer a cached copy is allowed to live, the
faster subsequent reads are and the cheaper the origin's load, but the longer
a stale copy can be served after the source content changes. This pattern
resolves the tension by moving invalidation from a runtime decision to a
deploy-time or purge-time event, trading real-time freshness for near-instant
read latency almost everywhere.

**Cost versus elasticity.** Object storage and CDN egress are billed by bytes
transferred and requests served, with no fixed server cost, which means the
pattern's cost curve tracks traffic almost linearly and there is effectively
no capacity planning. The competing force is that at very high, sustained
volume, a well-utilized dedicated server or a self-hosted cache can be cheaper
per gigabyte than commercial CDN egress, so the pattern's elasticity is not
free, it is a premium paid for not having to plan capacity.

**Simplicity versus expressiveness.** Removing the application server removes
an entire category of runtime failure, no process to crash, no memory leak to
chase, no dependency to patch under load. The competing force is that the
same removal takes away anything that requires per-request server-side
logic, authentication that must check a database, A/B tests that must be
decided server-side, content that must be assembled from a user's private
state. Every one of those needs is pushed either to the client, to a separate
API the static page calls, or to an edge function layered on top of the
pattern, which dimension 8 covers.

**Consistency versus availability.** A CDN's many edge caches are, by
definition, multiple copies of the same data that are not updated atomically.
During a deploy or a purge, different readers in different regions can
observe different versions of the site for a window of seconds to minutes.
This is an explicit and usually acceptable trade for a static site, because
the alternative, a single consistent origin, reintroduces the latency and
single point of failure the pattern exists to remove.

**Operability versus cost of misuse.** Team topology matters here in a
practical way. Because the pattern removes the server, it also removes the
team that would normally own that server's on-call rotation, patching
schedule, and capacity plan. That operational burden does not vanish, it
moves to the CDN and object storage vendor, which is a genuine win for a
small team, but it means the team loses direct visibility into and control
over the infrastructure that is now serving their traffic, and must instead
learn the vendor's cache-control semantics, purge API, and observability
surface.

## 4. Applicability and non-applicability

**Reach for this pattern when.**

- The content is identical for all readers, or can be varied entirely at the
  edge, such as by locale, by an A/B bucket read from a cookie, or by device
  type, without a database round trip.
- The publish cadence is build-and-deploy, not per-write. A blog, a docs
  site, a marketing page, a compiled single-page app, a changelog.
- The audience is geographically distributed and read-heavy, so edge caching
  produces a real latency win over a single-region origin.
- The team wants to eliminate server operations entirely for this surface,
  no patching, no capacity planning, no process supervision.
- The content can tolerate eventual, deploy-triggered freshness rather than
  strict read-your-writes consistency across every reader worldwide.
- Cost needs to track traffic closely, with near-zero fixed infrastructure
  spend at low volume.

**Do NOT reach for this pattern when.**

- The response depends on per-request server-side state that cannot be
  resolved from a client-visible cookie, header, or public parameter, for
  example a page that must query a database for the current authenticated
  user's private dashboard data. Serve that from an application server or an
  edge function backed by a data layer, not from a static cache.
- The content changes on every write and readers require strict, immediate
  consistency, for example a live order book or a chat transcript. Caching
  such content, even briefly, produces observably wrong behavior.
- The workload needs server-side rendering per request for reasons other
  than personalization, for example computing a response that depends on
  live, expensive aggregation. That belongs behind a proper backend, possibly
  fronted by the caching patterns in dimension 13, not served as static
  bytes.
- Regulatory or contractual data residency requirements forbid the content
  from being replicated to points of presence in certain jurisdictions. A
  general-purpose CDN's edge network usually cannot be constrained precisely
  enough to satisfy strict data-residency law without a specialized,
  region-locked configuration, which erodes the pattern's core benefit.
- The site is small, internal, and low-traffic enough that a single small
  server plus a reverse proxy is simpler to reason about than a build
  pipeline, an object store, and a CDN cache-invalidation strategy. The
  pattern has real operational surface of its own, it is not free just
  because there is no server process.

## 5. Structure

The pattern has four participants, though in the simplest deployments the
first two are collapsed into one vendor product.

- **Origin store.** The durable, canonical location for the built artifact,
  typically an object store such as Amazon S3, Google Cloud Storage, or
  Cloudflare R2, or a Git-backed build pipeline that deploys directly into a
  CDN's own storage, as Netlify, Vercel, Cloudflare Pages, and GitHub Pages
  do. The origin's job is durability and being the single source of truth the
  CDN falls back to on a cache miss.
- **Content delivery network.** A distributed network of edge servers, each
  holding a cached copy of some subset of the origin's content, chosen so
  that a reader's request is answered by the geographically or
  topologically nearest edge node rather than by the origin itself. Wikipedia
  describes the general architecture as edge servers serving client requests
  from many points of presence, falling back to an origin server that
  provides the source content when an edge node does not yet have a fresh
  copy (Wikipedia, Content delivery network, verified 2026-08-02,
  https://en.wikipedia.org/wiki/Content_delivery_network).
- **Build pipeline.** The process, run in CI or a vendor's own build service,
  that turns source such as Markdown, JSX, or Sass into the final static
  artifact and pushes it to the origin. This participant is not strictly
  required, some content is authored directly as static HTML, but in almost
  every real deployment it exists.
- **Cache invalidation controller.** The mechanism, whether a
  deploy-triggered purge, a time-to-live expiry, or a content-hashed
  filename, that decides when an edge node's cached copy is considered stale
  and must be refetched from the origin. This is the participant that
  resolves the latency versus freshness force from dimension 3, and its
  design is the single most consequential decision in an implementation of
  this pattern.

## 7. Dynamics

**Deploy flow.** A content change lands in the source repository. The build
pipeline runs, compiling source into a set of static files, most systems
apply content hashing to filenames at this stage, turning `app.js` into
`app.a1b2c3.js`, so that a changed file gets a new, unique URL. The pipeline
pushes the built artifact to the origin store as a new, complete version,
either by overwriting the same bucket path in an S3-style setup, or by
publishing an entirely new, independently addressable deploy, which is
Netlify and Vercel's atomic-deploy model, where every deploy gets its own
permanent, previewable URL before being promoted to production. Once the
origin has the new version, an invalidation signal is sent to the CDN, either
a targeted purge of the changed paths or, for platforms using content-hashed
filenames plus an unhashed entry HTML file, a purge scoped to just that entry
file, since the hashed assets never need invalidating at all because their
URL itself changed.

**Read flow, cache hit.** A reader's browser resolves the site's domain to an
anycast or geo-DNS address that routes to the nearest edge point of presence.
The edge node checks whether it holds a fresh copy of the requested path. If
it does, per the CDN's cache-control policy, it serves the bytes directly
from edge memory or edge disk, typically in single-digit to low-double-digit
milliseconds, with no round trip to the origin at all.

**Read flow, cache miss.** If the edge node has no copy, or its copy has
expired per a time-to-live, it makes a single request to the origin store,
receives the bytes, stores a copy for future requests, and serves the reader.
This adds the origin round-trip latency to that one request, which is why
CDNs use techniques like tiered caching, a mid-tier cache shared by many edge
nodes so only the first edge node globally pays the full origin round trip,
to keep the miss penalty rare and localized.

**Purge propagation.** When a purge is issued, it does not take effect
everywhere instantaneously. Different CDNs give different propagation-time
guarantees, ranging from a handful of seconds for the largest commercial
providers to longer for smaller networks, and during that window some edge
nodes serve the old content while others already serve the new content. This
is the concrete, observable manifestation of the consistency-versus-
availability force from dimension 3.

```
Deploy:  Build --> Origin (new version) --> Purge signal --> [EU][US][AP][SA]
                                                                |    |   |   |
                                                        (each edge independently
                                                         drops or replaces its
                                                         cached copy, at its own
                                                         propagation delay)

Read (hit):    Reader -> nearest Edge -> [fresh copy found] -> 200 OK, fast
Read (miss):   Reader -> nearest Edge -> [no/stale copy] -> Edge -> Origin
                                                            -> 200 OK -> cache
                                                            -> reply to Reader
```

## 8. Implementation variants

**Bucket-plus-CDN, manually wired.** An S3 bucket, or GCS, or R2, configured
for static website hosting, fronted by a separate CDN distribution such as
CloudFront, Cloudflare, or Fastly, that the team configures explicitly,
including origin access controls, cache-control headers, and purge
automation in CI. This is the most flexible variant and the most
operationally involved. Notably, AWS's own current guidance steers new users
away from wiring S3 website hosting directly and toward a managed layer, AWS
Amplify Hosting, that handles the CDN wiring for them, stating that Amplify
Hosting is "a fully managed service that makes it easy to deploy your
websites on a globally available content delivery network (CDN) powered by
Amazon CloudFront" (AWS S3 User Guide, Hosting a static website using Amazon
S3, verified 2026-08-02,
https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteHosting.html). A
specific, non-obvious limitation of the raw S3 website-endpoint variant is
that the S3 website endpoint itself does not support HTTPS, which is
precisely why a CDN or a KMS-encrypted bucket both require a CloudFront layer
in front, per the same AWS documentation's note that SSE-KMS-encrypted
buckets require a CloudFront distribution with origin access control because
SSE-KMS does not support anonymous access.

**Git-integrated, atomic-deploy platforms.** Netlify, Vercel, and Cloudflare
Pages collapse the build pipeline, origin, and CDN into one product. A push
to a connected Git repository triggers a build, and the result is published
as an atomic, immutable deploy that gets its own permanent URL before
optionally being promoted to the production domain, which means a broken
build never partially overwrites a working site and a bad deploy can be
instantly rolled back to the previous atomic snapshot. Cloudflare Pages
specifically documents deploying "full-stack applications that are instantly
deployed to the Cloudflare global network", via Git integration, direct
upload of prebuilt assets, or a CLI tool (Cloudflare Docs, Cloudflare Pages,
verified 2026-08-02, https://developers.cloudflare.com/pages/).

**Repository-native hosting.** GitHub Pages takes files "straight from a
repository on GitHub, optionally runs the files through a build process, and
publishes a website" (GitHub Docs, About GitHub Pages, verified 2026-08-02,
https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages),
requiring either a repository literally named `<owner>.github.io` for a user
or organization site, or a designated branch or folder for a project site.
This variant trades configuration flexibility for near-zero setup, and is
documented as limiting each account or repository to one Pages site.

**Edge-function augmented static hosting.** A hybrid variant, sometimes
called static plus edge compute, where the bulk of the site is static and
cached normally, but specific paths are handled by a small function that
runs at the CDN's edge nodes rather than at a central origin, for example to
rewrite a response header, run an A/B test decision from a cookie, or perform
authentication token validation before serving a protected static asset.
Cloudflare Pages Functions, Netlify Edge Functions, and Vercel Edge
Middleware are examples of this variant. This is the mechanism that lets
teams keep almost all of the pattern's simplicity while adding just enough
per-request logic to satisfy a requirement dimension 4 would otherwise rule
the pattern out for.

**Incremental static regeneration and static export hybrids.**
Framework-level variants, notably in Next.js, where pages are built
statically but can be regenerated on a schedule or on-demand after
deployment, without a full rebuild of the whole site. This blurs the line
between this pattern and server-side rendering, and is a deliberate
compromise. Most of a page's lifetime is served as a plain cached static
file, but the staleness window is bounded and controllable per page rather
than fixed for the whole site.

## 9. Known production uses

- **Amazon S3 plus Amazon CloudFront**, documented directly by AWS as the
  canonical pattern for a globally available, HTTPS-served static website,
  with current AWS guidance recommending AWS Amplify Hosting as the managed
  wrapper around exactly this S3-plus-CloudFront combination (AWS S3 User
  Guide, Hosting a static website using Amazon S3, verified 2026-08-02,
  https://docs.aws.amazon.com/AmazonS3/latest/userguide/WebsiteHosting.html).
- **GitHub Pages**, used to serve GitHub's own documentation ecosystem and
  millions of open-source project sites directly from repository content,
  described by GitHub as taking files "straight from a repository on GitHub"
  and publishing them as a live site (GitHub Docs, About GitHub Pages,
  verified 2026-08-02, https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages).
- **Cloudflare Pages**, Cloudflare's own product for deploying static and
  full-stack sites "instantly deployed to the Cloudflare global network",
  integrated with Cloudflare Workers via Pages Functions for edge compute
  (Cloudflare Docs, Cloudflare Pages, verified 2026-08-02,
  https://developers.cloudflare.com/pages/).
- **Akamai's content delivery network**, the commercial origin of this
  pattern's CDN half, founded in 1998 out of MIT research on consistent
  hashing specifically to solve the middle-mile bottleneck that congested web
  traffic in the late 1990s, and still one of the largest commercial CDNs
  serving static and dynamic content for major web properties today
  (Wikipedia, Akamai Technologies, verified 2026-08-02,
  https://en.wikipedia.org/wiki/Akamai_Technologies).
- **The general practice of serving library assets, stylesheets, and
  JavaScript bundles from CDNs** rather than an application's own servers is
  documented by the Mozilla Developer Network as a standard technique,
  explicitly noting that entire websites can be served from CDNs,
  particularly static websites comprised of HTML, CSS, and JavaScript (MDN
  Web Docs, CDN glossary entry, verified 2026-08-02,
  https://developer.mozilla.org/en-US/docs/Glossary/CDN).

## 10. Consequences

**Positive.**

- Removes an entire class of runtime failure. There is no application
  process to crash, leak memory, or exhaust connections under load, because
  there is no application process serving these requests.
- Scales to effectively unbounded read traffic without capacity planning,
  because the CDN's edge fleet, not a fixed pool of application servers,
  absorbs the load.
- Produces very low read latency for a globally distributed audience, since
  the response is served from the geographically nearest edge node rather
  than a single-region origin.
- Cost tracks traffic closely with near-zero fixed cost at low volume, which
  is a meaningful advantage for early-stage projects and side content that
  may see zero traffic for long stretches.
- Deploys are trivially reproducible and, on the atomic-deploy platforms,
  instantly reversible, because a broken deploy is just a different immutable
  version, not a partially-applied change to a running system.
- Attack surface for the serving layer shrinks dramatically. There is no
  server-side code execution path to compromise for the static portion of
  the site, only the CDN and origin configuration itself.

**Negative.**

- Any requirement for per-request, server-side computed content forces the
  team either onto an edge-function hybrid, per dimension 8, or a wholly
  separate backend, adding architectural complexity the pure pattern was
  meant to avoid.
- Freshness becomes probabilistic during the purge propagation window,
  meaning different readers can legitimately see different content for a
  period after a deploy, which is unacceptable for some classes of content.
- The team loses direct operational control and visibility. Debugging a
  regional slowdown or a cache-poisoning incident now requires understanding
  the vendor's edge network behavior, not just their own server logs.
- Vendor lock-in accrues quietly. Cache-control conventions, purge APIs,
  edge-function runtimes, and deploy-preview URL formats differ enough
  between CDN providers that migrating a mature deployment is nontrivial
  engineering work, not a configuration change.
- At sustained very high traffic volumes, commercial CDN egress billing can
  exceed the cost of running dedicated, well-utilized infrastructure, so the
  pattern's cost advantage is not universal. It is strongest at low and
  bursty traffic and weakens as scale grows large and steady.

## 11. Failure modes and misuse

| Symptom | Cause | Fix |
|---|---|---|
| A deployed content change is visible to some readers immediately and to others for minutes afterward, and the team treats this as a bug in the deploy pipeline | The purge propagation window across the CDN's edge fleet was never accounted for; the team assumed a deploy was globally atomic | Set expectations and monitoring around the CDN's documented purge propagation time; for content that must appear atomically everywhere, gate the user-visible change behind a feature flag read at request time rather than relying on cache purge timing |
| Readers occasionally receive a stale, broken version of the site's JavaScript bundle that no longer matches the current HTML, causing a runtime error referencing an undefined function | The HTML entry file was cached with a long time-to-live and was not purged on deploy, while the JavaScript bundle filename was content-hashed and changed, so a reader's browser held an old HTML page pointing at an asset URL that had since been superseded, or an old cached HTML pointed at a bundle URL that no longer matched the currently served bundle's exports | Cache the unhashed entry HTML with a very short or no time-to-live and purge it explicitly on every deploy, while caching content-hashed assets with an effectively infinite time-to-live, since their filename itself changes when their content changes |
| A private or unpublished draft page becomes publicly reachable by anyone who guesses or is given its URL | The team assumed that not linking to a static file was equivalent to it being private, but object storage and CDN edges will happily serve any object at a known path to any requester unless access is explicitly restricted | Never rely on obscurity for anything sensitive served by this pattern; put access-restricted content behind signed URLs, an edge-function auth check, or do not serve it from the static origin at all |
| The site works correctly in every region except one, where readers consistently see an old version or elevated errors | A single edge point of presence in that region has a corrupted or unusually long-lived cache entry that a global purge did not reach, due to a partial outage or a bug in the CDN's purge propagation for that node | Use the CDN's per-node or regional purge diagnostics if available, and add synthetic monitoring from multiple regions so a single-region staleness incident is detected automatically rather than discovered from a support ticket |
| Build costs and deploy times grow linearly and eventually become the team's biggest operational bottleneck, with a routine content edit taking many minutes to go live | The entire site is rebuilt and re-uploaded on every single content change, even a one-line fix to a single page, because the build pipeline has no incremental build support | Adopt incremental builds, content-hashed asset caching between builds, or a framework with incremental static regeneration so a small content change does not force a full-site rebuild |
| A CDN vendor bill spikes unexpectedly after what the team believed was a routine traffic increase | A misconfigured cache-control header, or a query-string parameter the CDN was not configured to ignore, caused effectively every request to be treated as a unique, uncacheable URL, so almost every request fell through to the origin and, on a bandwidth-billed origin, multiplied cost | Audit cache-control headers and the CDN's cache-key configuration, meaning which query parameters and headers vary the cache key, after any traffic anomaly, and set billing alerts scoped to origin egress specifically, not just total spend |

## 12. Trade-off matrix

| Force | Static Content Hosting | Application server rendering per request | Gateway offloading of static assets to a reverse proxy in front of a server |
|---|---|---|---|
| Read latency for a globally distributed audience | Lowest, served from the nearest edge node with no origin round trip on a cache hit | Highest, every request pays the round trip to a single-region or few-region server | Moderate, improved over raw origin but bounded by the reverse proxy's own placement, usually not globally distributed |
| Operational burden | Lowest, no application process to run or patch for the static surface | Highest, full server lifecycle, process supervision, patching, capacity planning | Moderate, still runs and patches an application server, but the proxy absorbs static-asset load |
| Freshness guarantee | Eventual, bounded by purge propagation after a deploy | Immediate, every request computed fresh | Immediate for the dynamic path, eventual for cached static assets behind the proxy |
| Cost at low, bursty traffic | Very low, near-zero fixed cost | Higher, a server must be provisioned even when mostly idle | Higher than pure static hosting, a server still runs continuously |
| Fit for per-request personalization | Poor without an edge-function hybrid | Excellent, native | Excellent for the dynamic path, unchanged from a plain application server |
| Attack surface for the serving layer | Smallest, no request-time server code for the static portion | Largest, full application code executes on every request | Reduced for static assets, unchanged for the dynamic path behind the proxy |

## 13. Related and incompatible patterns

**Cache-Aside** shares this pattern's fundamental idea, check a fast cache
before falling to a slower source of truth, but Cache-Aside is a
runtime-application-code pattern where the application itself checks and
populates a cache on each request, whereas Static Content Hosting pushes that
same idea down into infrastructure that requires no application code at all
for the cached path.

**Gateway Offloading** is the pattern this entry's reverse-proxy-in-front-of-
a-server row in dimension 12 represents, and the two compose naturally. A
system can serve its purely static assets through full Static Content
Hosting while routing its dynamic API traffic through a gateway that
offloads concerns like TLS termination and compression, without those two
paths interfering with each other.

**Sharding** is largely orthogonal but relevant when the origin store itself
holds enough content that a single bucket or storage account becomes a
bottleneck for the build pipeline's write throughput, at which point content
may be sharded across multiple storage buckets fronted by a single CDN
configuration.

**Geode**, the deployment pattern of running multiple active regions serving
from local data, is a close cousin at the infrastructure level. A CDN's edge
network is, functionally, a purpose-built, read-only geode for a single
class of workload, static bytes, which is why teams that need the Geode
pattern for a full read-write application often still layer Static Content
Hosting on top for that application's public-facing static assets.

**External Configuration Store** composes with this pattern when a static
site's client-side JavaScript needs runtime configuration, such as feature
flags or an API base URL, that must not be baked into the immutable static
build. That configuration is fetched at page load from a small, separately
updatable endpoint rather than requiring a full site rebuild for a
configuration change.

**Incompatible or in tension.** Any pattern that assumes strict, immediate,
system-wide read consistency, such as patterns built around distributed
consensus or synchronous replication, is fundamentally in tension with this
pattern's eventual, purge-bounded freshness model, and the two should not be
applied to the same piece of content.

## 14. Refactoring path in and out

**Introducing the pattern into an existing server-rendered site.** Start by
auditing which routes genuinely require per-request server computation and
which do not; a surprising fraction of most sites, marketing pages,
documentation, blog posts, are static once written. Extract those routes into
a static build step, either with a static site generator or a build-time
export mode of the existing framework, and deploy the output to an origin
plus CDN, initially alongside the existing server for the routes that remain
dynamic, fronted by a router or DNS split that sends static-eligible paths to
the CDN and everything else to the server. Once the static path is proven
stable, progressively migrate more routes, converting per-request logic that
turns out to be personalization-only into an edge-function check against a
cookie rather than a full server round trip, per the hybrid variant in
dimension 8. Retire the origin server's responsibility for those routes only
once the CDN path has been serving production traffic successfully and the
team has confidence in its purge and rollback tooling.

**Removing the pattern.** The pattern stops earning its place when the site
develops a hard, unavoidable requirement for synchronous, per-request
server-side state that cannot be resolved at the edge, or when the team
determines, based on measured cost, that sustained traffic volume has made
CDN egress billing more expensive than running dedicated infrastructure. The
removal path is the reverse of the introduction path. Stand up an application
server capable of serving the content dynamically, verify it produces
byte-identical or acceptably equivalent output to the static build for a
representative sample of pages, cut traffic over gradually via the same
router or DNS split mechanism used to introduce the pattern, and only then
decommission the static build pipeline and purge the CDN of the retired
content. A team should keep the static origin as a cold, disaster-recovery
fallback for a period after cutover, since it costs almost nothing to leave
in place and provides an immediate rollback path if the new dynamic serving
layer misbehaves.

## 15. Testing and verification

Testing this pattern splits cleanly into build-time correctness and
runtime-behavior correctness, and conflating the two is the most common
testing mistake.

**Build-time correctness** is tested the same way any deterministic
transformation is tested. Given a fixed source input, assert the build
produces the expected output files, with the expected content-hashed
filenames, and that no build step silently swallowed an error, such as a
broken Markdown link or a missing image reference, that would otherwise ship
a broken page to production. This is straightforward to automate in CI and
should run on every pull request, before any deploy is attempted.

**Runtime behavior**, specifically cache-control headers, purge propagation,
and edge-function logic, is harder to unit test because it depends on the
actual CDN's behavior, not just the built artifact. The practical approach is
a smoke test run against the CDN's own domain immediately after every
deploy, checking that a known-changed page now returns the new content and
that its response headers show the expected cache-control policy, combined
with a synthetic monitoring probe run from multiple geographic regions on an
ongoing schedule so that a single-region staleness or outage, per dimension
11, is caught automatically rather than by a user report. This pattern is one
where testing what the CDN vendor actually does in production is not
optional; the built artifact being correct says nothing about whether the
edge network is serving it correctly.

What becomes easier to test because of this pattern is worth naming
explicitly. The absence of an application server removes an entire category
of test, there is no need to mock a database, an authentication session, or a
request-scoped dependency for the static-serving path, because none of those
exist on that path.

## 16. Observability signals

A healthy deployment of this pattern shows a CDN cache hit ratio that is high
and stable, typically in the high nineties of a percent for a mature site
with well-tuned cache-control headers, because a low hit ratio means most
traffic is falling through to the origin, defeating the purpose of the
pattern and inflating both latency and origin egress cost. Origin request
count and origin bandwidth should track roughly with deploy frequency and new
content volume, not with total reader traffic; if origin bandwidth scales
linearly with total traffic instead of staying flat between deploys, that is
the single clearest signal that caching is misconfigured, per the failure
mode in dimension 11 about an uncacheable query-string parameter.

Purge latency, the measured time between issuing a purge and every edge node
reflecting the new content, should be tracked explicitly and alerted on if it
exceeds the CDN vendor's documented service-level expectation, since a silent
regression here is exactly what produces the regional-staleness failure mode.
Edge error rates, meaning 4xx and 5xx responses served directly by the CDN,
distinct from errors the origin itself returns, should be monitored
separately from origin error rates, because a spike in edge-served errors
with no corresponding spike at the origin usually indicates a CDN-side
configuration or outage issue rather than a problem in the built content
itself. Finally, per-region latency percentiles, not just a single global
average, are the correct dashboard for this pattern, because the entire
value proposition is uniform low latency across geography, and a global
average can hide a badly served region behind many well-served ones.

## 17. Security and privacy implications

The removal of a per-request application server genuinely shrinks the attack
surface for the static-serving path. There is no server-side code execution
to exploit for content that is served as plain bytes from an edge cache.
That said, several security implications remain squarely within this
pattern's scope. Origin store access control is critical; a misconfigured
object storage bucket that allows public listing or public write access can
leak unpublished content or allow an attacker to overwrite production
content, and this is a well-documented, recurring class of real-world
incident with public object storage generally. Any content that must not be
publicly readable must not be placed on the static origin at all, or must be
placed behind a signed-URL or edge-function authorization check, since, as
noted in dimension 11, an unlinked static file is not a private file, it is
simply an unadvertised public one.

CDN edge nodes are also, by their nature, third-party infrastructure sitting
between every reader and the site's content, which means the CDN operator has
technical visibility into all traffic to the site, a privacy consideration
that should be disclosed in the site's own privacy documentation where
applicable, and a supply-chain trust dependency that should be weighed the
same way any third-party dependency is weighed. Content delivered through
this pattern should still be served over HTTPS end to end, from reader to
edge and from edge to origin on a cache miss; a static origin's own website
endpoint may not support HTTPS directly, which is precisely why the AWS
documentation requires a CloudFront layer for encrypted or HTTPS-served S3
static sites rather than exposing the raw website endpoint (AWS S3 User
Guide, verified 2026-08-02). Finally, subresource integrity checks are a
relevant mitigation when a site pulls static assets, scripts in particular,
from a third-party CDN it does not control, since a compromise of that
third-party CDN could otherwise inject arbitrary code into every page that
references it, a concern the Mozilla Developer Network documentation on CDNs
explicitly names as a downside of relying on shared, third-party-hosted
static assets (MDN Web Docs, CDN glossary entry, verified 2026-08-02).

## Code examples

The examples below show the pattern from three different vantage points. A
build-time script that produces content-hashed filenames, which is the
mechanism that makes long-lived edge caching safe, per dimension 8 and the
failure mode in dimension 11, a deploy-time uploader that pushes an artifact
to an object store with correct cache-control headers, and a minimal
reference server that demonstrates the two cache policies at read time.
These are deliberately small and self-contained, not framework scaffolding.

### TypeScript. content-hashed asset manifest builder (Node.js)

Simulates the core of what a static site generator's build step does,
hashing each asset's content, renaming the asset to include the hash, and
producing a manifest so the entry HTML can reference the correctly-hashed
URLs. Long-lived, effectively infinite, cache-control headers are safe for
these hashed files precisely because a content change always produces a new
filename.

```typescript
import { createHash } from "node:crypto";

interface Asset {
  path: string;
  content: string;
}

interface HashedAsset {
  originalPath: string;
  hashedPath: string;
  cacheControl: string;
}

function hashContent(content: string): string {
  return createHash("sha256").update(content).digest("hex").slice(0, 10);
}

function buildManifest(assets: Asset[]): Map<string, HashedAsset> {
  const manifest = new Map<string, HashedAsset>();
  for (const asset of assets) {
    const hash = hashContent(asset.content);
    const dot = asset.path.lastIndexOf(".");
    const hashedPath =
      dot === -1
        ? `${asset.path}.${hash}`
        : `${asset.path.slice(0, dot)}.${hash}${asset.path.slice(dot)}`;
    manifest.set(asset.path, {
      originalPath: asset.path,
      hashedPath,
      cacheControl: "public, max-age=31536000, immutable",
    });
  }
  return manifest;
}

function rewriteEntryHtml(html: string, manifest: Map<string, HashedAsset>): string {
  let output = html;
  for (const [original, entry] of manifest) {
    output = output.split(original).join(entry.hashedPath);
  }
  return output;
}

const assets: Asset[] = [
  { path: "app.js", content: "console.log('build one');" },
  { path: "styles.css", content: "body { margin: 0; }" },
];

const manifest = buildManifest(assets);
const entryHtml = `<script src="app.js"></script><link rel="stylesheet" href="styles.css">`;
const rewritten = rewriteEntryHtml(entryHtml, manifest);

for (const [original, entry] of manifest) {
  console.log(`${original} -> ${entry.hashedPath} (${entry.cacheControl})`);
}
console.log(rewritten);
```

Compiled and run with `npx tsc` and `node`, verified 2026-08-02. Output.

```
app.js -> app.60926fd3b3.js (public, max-age=31536000, immutable)
styles.css -> styles.3e67b4a950.css (public, max-age=31536000, immutable)
<script src="app.60926fd3b3.js"></script><link rel="stylesheet" href="styles.3e67b4a950.css">
```

### Python. deploy-time cache-control planner and purge-set calculator

Represents the decision a deploy script must make for every file in a build,
whether it is content-hashed, meaning long cache with no purge needed since
its URL already changed, or unhashed, meaning short cache that must be
explicitly purged. This is the piece of logic that, when wrong, produces the
entry-HTML-versus-bundle mismatch failure mode from dimension 11.

```python
from dataclasses import dataclass
import hashlib
import re


@dataclass
class DeployPlan:
    path: str
    cache_control: str
    requires_purge: bool


HASHED_FILE_PATTERN = re.compile(r"\.[0-9a-f]{8,}\.[a-zA-Z0-9]+$")


def content_hash(data: bytes) -> str:
    return hashlib.sha256(data).hexdigest()[:10]


def plan_deploy(files: dict[str, bytes]) -> list[DeployPlan]:
    plans: list[DeployPlan] = []
    for path, content in files.items():
        is_hashed = bool(HASHED_FILE_PATTERN.search(path))
        if is_hashed:
            plans.append(
                DeployPlan(
                    path=path,
                    cache_control="public, max-age=31536000, immutable",
                    requires_purge=False,
                )
            )
        else:
            plans.append(
                DeployPlan(
                    path=path,
                    cache_control="public, max-age=60, must-revalidate",
                    requires_purge=True,
                )
            )
    return plans


def purge_set(plans: list[DeployPlan]) -> list[str]:
    return [p.path for p in plans if p.requires_purge]


if __name__ == "__main__":
    build_output = {
        "index.html": b"<html>v2</html>",
        "app.9f6d2f8f31.js": b"console.log('build one');",
        "robots.txt": b"User-agent: *\nAllow: /",
    }
    plans = plan_deploy(build_output)
    for plan in plans:
        print(f"{plan.path}: {plan.cache_control} purge={plan.requires_purge}")
    print("Purge set:", purge_set(plans))
```

Run with `python3`, verified 2026-08-02. Output.

```
index.html: public, max-age=60, must-revalidate purge=True
app.9f6d2f8f31.js: public, max-age=31536000, immutable purge=False
robots.txt: public, max-age=60, must-revalidate purge=True
Purge set: ['index.html', 'robots.txt']
```

### Go. minimal cache-aware static file server (local reference model)

A team building or testing against this pattern locally, before deploying to
a real CDN, benefits from a small reference server that reproduces the two
cache-control policies from the Python example above. This is not a
production CDN, it is a local stand-in that makes the pattern's contract
explicit and testable without external infrastructure.

```go
package main

import (
	"fmt"
	"net/http"
	"regexp"
	"strings"
)

var hashedFilePattern = regexp.MustCompile(`\.[0-9a-f]{8,}\.[a-zA-Z0-9]+$`)

func cacheControlFor(path string) string {
	if hashedFilePattern.MatchString(path) {
		return "public, max-age=31536000, immutable"
	}
	return "public, max-age=60, must-revalidate"
}

func staticHandler(files map[string]string) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		path := strings.TrimPrefix(r.URL.Path, "/")
		if path == "" {
			path = "index.html"
		}
		body, ok := files[path]
		if !ok {
			http.NotFound(w, r)
			return
		}
		w.Header().Set("Cache-Control", cacheControlFor(path))
		w.Write([]byte(body))
	}
}

type responseRecorder struct {
	header http.Header
	body   []byte
	status int
}

func (r *responseRecorder) Header() http.Header          { return r.header }
func (r *responseRecorder) Write(b []byte) (int, error)  { r.body = append(r.body, b...); return len(b), nil }
func (r *responseRecorder) WriteHeader(status int)        { r.status = status }

func main() {
	files := map[string]string{
		"index.html":        "<html>v2</html>",
		"app.9f6d2f8f31.js": "console.log('build one');",
	}
	handler := staticHandler(files)
	for _, path := range []string{"index.html", "app.9f6d2f8f31.js"} {
		req, _ := http.NewRequest("GET", "/"+path, nil)
		rec := &responseRecorder{header: http.Header{}}
		handler(rec, req)
		fmt.Printf("%s -> Cache-Control: %s\n", path, rec.header.Get("Cache-Control"))
	}
}
```

Compiled and run with `go run`, verified 2026-08-02. Output.

```
index.html -> Cache-Control: public, max-age=60, must-revalidate
app.9f6d2f8f31.js -> Cache-Control: public, max-age=31536000, immutable
```
