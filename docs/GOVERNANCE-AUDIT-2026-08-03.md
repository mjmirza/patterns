# Governance Audit, 2026-08-03

Requested by the repository owner as a full trust, content-model, tooling,
governance, and security review. This document is the audit, the gap
analysis, and the prioritized plan. Section 5 lists what shipped in the
same change as this audit. Everything else is documented as open work,
not implemented, and not claimed as done.

## 1. What already exists (confirmed by reading the repo, not assumed)

- Four CI jobs in `.github/workflows/ci.yml`. structure and prose, code
  samples compile, citations resolve, markdown style. All four ran green
  on every merged PR through #16.
- `tools/check-structure.py` enforces 18 required section headings, 5
  required frontmatter fields, a controlled `maturity` vocabulary (5
  values), a 3-language code minimum, a 1200-word prose minimum, and bans
  em and en dashes.
- `tools/validate-refs.py` HEAD/GET-probes every cited URL, with a
  `.ref-cache.json` cache and an `ALLOW_UNREACHABLE` host allowlist for
  bot-blocking-but-live publishers. It checks resolution only, not that
  the cited page actually supports the specific claim next to it.
- `tools/check-code.py` compiles or syntax-checks every fenced code block
  in six languages, Python, TypeScript, Java, Go, Rust, Swift, with a
  cross-block retry for same-file dependent snippets.
- `tools/check-prose.py`, `tools/gen-indexes.py`, `tools/next-batch.py`,
  `docs/AUTHORING-QUEUE.json`, `docs/ENTRY-TEMPLATE.md`, `ATTRIBUTION.md`,
  and a weekly `refresh-citations.yml` job that re-probes every citation
  and commits the refreshed cache.
- A branch-per-batch, PR-per-batch discipline with a 4-eyes merge gate
  (`pr-review-verdict.sh`), squash merges, and CI required green before
  every merge, enforced by tooling outside this repository.

## 3. Gap analysis, by category

### Trust

- Citation resolution is verified in CI. Citation relevance, whether the
  cited page actually supports the specific sentence next to it, is not
  mechanically checked anywhere. This is the exact gap the owner named,
  a URL returning HTTP 200 is not proof it supports the claim. No tooling
  exists for this yet. It needs either per-claim evidence tagging, a real
  schema change, or a human spot-check process. Not implemented here.
- "Master level" is asserted in the README's first sentence with no
  linked, visible governance mechanism a reader can inspect to verify the
  claim. GOVERNANCE.md, MAINTAINERS.md, and reviewer ownership do not
  exist yet.
- Production-use claims inside entries are prose, not structured data.
  There is no machine-checkable distinction between explicitly documented
  use and inferred architectural similarity. `check-structure.py` only
  requires 3 named sources per entry, it does not classify their evidence
  strength.

### Content model

- No stable, permanent entry ID exists. An entry is identified only by
  its file path. Renaming a file breaks every inbound reference silently.
- No `schema/pattern.schema.json` or any machine-validated frontmatter
  schema exists. `check-structure.py`'s `REQUIRED_FRONTMATTER` list (5
  fields) is enforced by regex, not a versioned schema.
- `kind` (pattern vs anti-pattern vs principle vs technique vs mechanism)
  is not a frontmatter field. Family 04, Principles and Laws, is the only
  place this distinction is made, and only in README prose, not in data.
- No relationship model beyond the free-text `related` and
  `incompatible_with` frontmatter arrays (confirmed present, for example
  in `sidecar.md`). These are not validated against real entry IDs, so a
  typo or a renamed slug silently breaks the relationship with no CI
  failure.
- No decision-summary block (use when, avoid when, primary cost,
  reversibility) exists at the top of any entry. Dimension 4 covers
  similar ground but in prose form, not a scannable structured block.

### Governance

- GOVERNANCE.md, MAINTAINERS.md, CODE_OF_CONDUCT.md, SECURITY.md,
  CODEOWNERS, and any issue or PR template do not exist. There is no
  documented answer today to who decides maturity, how disputes are
  resolved, or who reviews a security-family entry.
- There is one repository owner and no reviewer specialization model.
  Given the breadth of families, distributed systems, security, AI,
  category theory, embedded systems, no single reviewer can credibly
  claim expert-level verification across all of them. This is a real,
  named risk, not a hypothetical one.

### Usability

- No documentation site exists. The repository is Markdown-only, browsed
  through GitHub's own renderer.
- `docs/BY-PROBLEM.md` and `docs/BY-LANGUAGE.md` are referenced in the
  README's "How to read it" section but do not exist on disk. This is the
  same class of false claim as `check-links.py`.
- No full-text search, no filtering by maturity or kind or family, no
  stable entry URLs beyond the GitHub file path.

### Tooling

- Zero test coverage existed for any validator before this change.
  `check-structure.py`, `check-prose.py`, `check-code.py`, and
  `validate-refs.py` have no fixtures proving they accept valid content
  and reject invalid content. A silent regression in any of them, a
  loosened regex, a broken frontmatter parser, would not be caught by CI,
  only if it happened to also break a real entry.
- `tools/gen-catalogue-status.py` and its test are the first validator
  test in this repository (see section 5). The remaining four validators
  are not yet covered, and closing that gap is the most valuable next
  step under P0.

### Security

- GitHub Actions in `.github/workflows/*.yml` are pinned to full commit
  SHAs already (confirmed by reading `ci.yml`), which is the correct
  practice and ahead of many repositories on this specific control.
- Workflow permissions default to `contents: read` on the main gate
  workflow (confirmed), which is correct. `refresh-citations.yml` needs
  `contents: write` to commit the refreshed cache, the minimum required
  for its job.
- No Dependabot or Renovate config, no CodeQL, no secret scanning
  workflow, no OpenSSF Scorecard badge or workflow exist. This repository
  has few code dependencies, Python stdlib plus an npm-installed
  `markdownlint-cli2` at CI time only, so the practical risk surface is
  small, but the controls are still absent and worth naming.

### Maintenance

- No `last_reviewed` or `next_review_due` frontmatter field exists. There
  is no mechanism to detect an entry that has gone stale, a cited API
  that moved, a framework version no longer current. The
  `refresh-citations.yml` weekly job re-probes URLs for liveness, which
  catches dead links but not content drift at a live URL.
- Two dead citations were found and fixed by hand during the last three
  authoring rounds, an AWS Step Functions URL truncated by a markdown
  line wrap, a LlamaIndex domain migration, a LangChain doc-page removal.
  Each was caught by `validate-refs.py --strict` in CI, the gate working
  as designed, but the pattern of vendor doc reorganizations will keep
  recurring and there is no proactive detection beyond the weekly
  liveness re-probe.

## 4. Unresolved risks

1. No reviewer beyond the repository owner has verified any published
   entry's domain accuracy. Every entry passing CI proves structural and
   citation-liveness compliance, not subject-matter correctness.
2. The `docs/SCOPE-TARGET.json` reconciliation (887 of a recorded 900) is
   honest about a 13-entry gap with no identified source. A future
   contributor could be tempted to close it by inventing entries, the
   file's own `gap_reason` field states plainly that doing so would
   violate the repository's no-fabrication rule, but there is no
   mechanical guard against it.
3. `check-code.py`'s TypeScript checker builds a shared scratch npm
   project on first use per CI run (confirmed by reading the tool). A
   registry outage during that install would fail the entire code-compile
   job for reasons unrelated to any entry's content. This is a known,
   accepted external dependency, not a defect, but a real availability
   risk worth naming.
4. The 3-language code-example minimum, flagged for reconsideration by
   the owner, has not been changed in this pass. It is a real, working
   requirement today. Changing it would touch the validity of every
   already-published entry and needs its own careful, isolated change,
   not a bundled edit inside a governance PR.

## 5. What shipped in this change (P0, safe and reviewable)

- `tools/gen-catalogue-status.py` generates `docs/PROGRESS.md`,
  `dist/catalogue-status.json`, `dist/catalogue-status.csv`, and rewrites
  the README family table and badges from real repository state. Wired
  into CI (the "Catalogue status is current" step) and into
  `make catalogue-check`, mirroring the existing `gen-indexes.py`
  pattern.
- `tools/gen-catalogue-status-test.py` is the first validator test in
  this repository. Proven red then green against the exact double-count
  bug found while building the generator, a queue entry already
  published was still counted as planned, inflating every target number.
- `docs/SCOPE-TARGET.json` is the single reconciliation record for the
  recorded 900-entry target vs the true, sourced total.
- Family 03, Refactoring Techniques, sourced for real from the official
  Fowler catalog at refactoring.com, live-fetched 2026-08-03, 66 entries,
  matching the inventory doc's own estimate.
- Three new families added with real, independently verifiable named
  patterns. 27, Mobile Architecture, 12 entries. 28, Embedded and
  Hardware-Software, 14 entries. 29, Real-Time Simulation, 9 entries,
  sourced from Nystrom's Game Programming Patterns.
- README corrections. "fourteen questions" to "eighteen", a Terminology
  section defining Published, Planned, Total catalogue scope, and
  maturity, the Quality Gates table corrected to name real tools and
  drop the non-existent link checker.
- `Makefile` fixed. the `links` target called a file that does not exist
  and would fail for any contributor running `make check`. Removed and
  replaced with a working `catalogue-check` target.

## 7. Claims that require human domain review

- Every published entry's domain accuracy. CI proves structure, citation
  liveness, and code compilation. It does not, and cannot, prove that a
  distributed-systems, security, or category-theory claim is correct.
- The `maturity` value assigned to each entry, canonical vs established
  vs emerging vs contested, is currently an authoring-time judgment call,
  not independently reviewed.
- The three newly-added families, mobile, embedded and hardware,
  real-time simulation, are real, named, sourced patterns, but no domain
  expert in those specific areas has reviewed the family scope for
  completeness or correct categorization.

## 8. What must be true before this repository can credibly call itself master-level

1. Every validator has a test proving it accepts good content and
   rejects bad content. P0, not done.
2. Every README claim resolves to a real, existing file or tool. P0,
   substantially fixed in this change, BY-PROBLEM.md and BY-LANGUAGE.md
   still open.
3. A documented citation-evidence policy exists and at minimum a sample
   of entries has been checked against it. P0, not done.
4. A named reviewer ownership model exists, even if it is currently one
   person per family rather than a full editorial board. P1, not done.
5. The catalogue status numbers in the README can never silently drift
   from reality. Done in this change, enforced by CI.
